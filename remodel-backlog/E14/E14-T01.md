# E14-T01 · Prompt editor and composer surface

## What it is

The composer is the box at the bottom of a thread (or centred in the new-thread hero) where the user writes what the agent should do next. This task owns its core: the prompt editor itself and the composer surface around it. The editor is a Tiptap/ProseMirror editor that shows mentions, skills, citations and context references as inline "atoms" (chips that behave like one character), continues Markdown lists, and handles paste of rich text, images, files and long text. Everything else in the composer (menus, attachments, chips, footer, stash, send) plugs into this surface and is owned by sibling tasks in this epic.

## When it is used

- Every message a user sends: first prompt of a new thread, follow-ups, steering while an agent runs, typed instructions for "Decline and tell", custom answers to agent questions.
- Editing long prompts with lists, task lists and code blocks.
- Pasting a screenshot, a stack trace, a file, or a block of rich text from a web page.

## How it works today

- **Entry points:** click the composer; type anywhere in the thread (type-to-focus, E14-T10); window regains focus (refocus); command palette closes (focus returns to composer); `F6` workspace-area navigation lands on "Message input". Placeholder text: "Ask anything, @tag files/folders, $use skills, or / for commands"; while a turn runs: "Queue a follow-up while it works".
- **Behaviour to preserve:**
  - One engine for both modes of the `richTextEnabled` client setting: rich (Markdown markers rendered) and plain. The stored prompt is Markdown-ish text with inline references such as `e6-context://v1/<kind>/<id>` links; the editor maps between four coordinate spaces (flat text, collapsed text where an atom is one character, Markdown, ProseMirror positions). Cursor position must survive switching modes and restoring drafts.
  - Inline atoms for `@` path mentions, `$` skills, `/skill:` references, assistant citations, `#` pull requests and context references (terminal, review comment, preview annotation, element). Mention chips can be dragged to reorder (`composerMentionDrag`).
  - List continuation on Enter, task lists, code blocks (inside a code block Enter inserts a newline; only Mod+Enter sends), Markdown markers.
  - Send keys follow Settings → General → Send shortcut: `enter` (Enter sends, Shift+Enter newline), `mod-enter` (always Mod+Enter), `mod-enter-multiline` (Enter sends single-line prompts, Mod+Enter once the prompt is multiline). Shift+Tab toggles plan mode when plan mode is available (E15-T08).
  - Paste: images and files become attachments (E14-T03); text of 32 KiB or more becomes a text-file attachment unless pasted with Cmd/Ctrl+Shift+V; copied chips paste back as chips (E14-T04); inline token paste (`composerInlineTokenPaste.ts`). Pasting plain text while nothing editable is focused is redirected into the composer.
  - IME composition is never interrupted (`isComposing` / keyCode 229 checks on Escape and Enter).
  - Caret scrolls into view inside the editor as it grows; the editor grows with content up to a max height.
  - Composer states hosted by the surface: empty, typed, multiline, with attachments, running (Stop, queue placeholder), deciding (approval/question/plan panel replaces or sits above the editor, E16), disabled (environment unavailable, connecting, preparing worktree, rewinding a checkpoint: the composer region is `inert`), over-limit validation (E14-T08), mobile-width expanded mode (`forceExpandedMobileComposer`).
  - The draft hero variant is the same component, centred and larger, docking to the bottom after the first send (180 ms transition today, owned by E13-T01 with this task supplying the composer half).
- **Surfaces:** web and desktop share it. Mobile has its own native editor (`E6ComposerEditor`, Swift/Kotlin) with inline chips, owned by E32-T03. Server: none.
- **Where the code lives:** `apps/web/src/components/chat/ChatComposer.tsx` (6,948 lines; memoised component with a props interface of roughly 150 fields and refs mirrored back to `ChatView`, such as `promptRef` and `composerImagesRef`), `components/ComposerPromptEditorTiptap.tsx` (1,412), `composer-rich-text-doc.ts` (811), `composer-rich-text.ts`, `composer-list-continuation.ts`, `composer-editor-mentions.ts`, `composer-logic.ts`, `composerInlineTokenPaste.ts`, `chat/ComposerSurface.tsx`, `chat/useComposerMultilinePrompt.ts`.

## Problems today

- `ChatComposer.tsx` is a 6.9k-line god component with no direct tests; menu items, stash, attachments, approvals and footer layout are all assembled inline.
- The ~150-field props interface and mirrored refs couple it tightly to the 11k-line `ChatView.tsx`; any ChatView state change risks a composer re-render (mitigated only by `memo` and stable-callback refs).
- Four coordinate spaces make cursor bugs easy; the logic is spread across several files.
- Layout depends on resize observers and measurement.
- Tiptap, ProseMirror and Shiki load on the main chat path.

## Remodel goals

- **Experience:** the composer becomes the "slate" of the design direction (§8 Composer): one raised surface (`--plane-raised`, `--radius-lg`) with four states that morph in place: idle, writing, running, deciding. Focus lights it with a 1 px `--primary-edge` border and a static `--light-key` wash faded in by opacity. The send button uses the `primary` fill with `primary-foreground`; disabled send uses `--plane-well` and `muted-foreground`, not today's dim navy disc.
- **Motion:** typing, caret movement, selection, IME and the editor's own growth while typing are on the design direction's instant list (§3.10): no animation, no added latency. The first send in the hero is set-piece 3.2 ("the words become the message"): the prompt text block travels to the first user message (`matchCut`, `dur.scene`) while the editor clears instantly; this task must expose the prompt block for that `layoutId`.
- **Performance:** keystroke to paint ≤ 32 ms p95 with no long task over 50 ms while a 50 events/s stream runs (architecture §3.1 "Input latency while streaming"). The editor must not re-render on streamed timeline events; it subscribes only to its own draft. Keep any v2 component file under 600 lines (architecture §2.2).

## Done when

- [ ] The v2 composer surface and editor live under `apps/web/src/next/features/composer/`, take a small typed view-model instead of ~150 props, and do not import `composerDraftStore` or `ChatView` (architecture §2.2 lint rule).
- [ ] Every behaviour in "Behaviour to preserve" has a parity check, including all three Send shortcut modes, rich and plain modes, IME, list continuation, code blocks and the 32 KiB paste rule.
- [ ] Drafts written by the legacy editor (prompt text with `e6-context://` references and legacy placeholders) open in the v2 editor with atoms and cursor intact (coordinate with E14-T06).
- [ ] Idle, writing, running, deciding and disabled states are designed and implemented in dark and light; keyboard users can reach every control; focus ring uses `primary-edge`.
- [ ] Input latency budget measured in the web harness during a streaming scenario.
- [ ] Unit tests for the coordinate mapping and paste rules; no static-markup render tests.
