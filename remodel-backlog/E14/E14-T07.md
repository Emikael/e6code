# E14-T07 · Prompt stash

## What it is

The prompt stash is a small shelf for prompts the user wants to set aside without sending. Cmd/Ctrl+S saves the current prompt with its attachments and context chips and clears the composer; pressing it again on an empty composer restores the single stashed prompt, or opens the stash menu when there are several. The stash is shared across threads and providers in one browser, holds up to 20 entries, and is saved locally.

## When it is used

- Mid-prompt, the user notices something more urgent and wants a clean composer.
- Carrying a prompt from one thread to another (stash here, restore there).
- Keeping a reusable instruction around for later in the day.

## How it works today

- **Entry points:** `composer.stash` keybinding (default `mod+s`, not in terminal focus); the stash badge in the composer footer (shows a count and pulses briefly after a stash); the stash drawer (arrow keys to move, Enter to restore, Delete/Backspace on a highlighted row to delete, Escape to close; capture-phase listener so the editor does not swallow the keys).
- **Behaviour to preserve:**
  - Stashing a non-empty composer saves prompt, images, files and context records (terminal excerpts, review comments, preview annotations), then clears the composer. Model and provider are deliberately not stashed (stash v2 is provider-agnostic).
  - Stashing an empty composer: restores the only entry if there is exactly one finished entry, otherwise toggles the menu.
  - Limit 20 entries; the oldest is evicted with the toast "Oldest stashed prompt discarded".
  - Images are re-encoded for the stash (`compressImageForStash`) and saved as data URLs within a 2,700,000-character budget per entry (about two screenshots). Images over budget are dropped and listed ("N images dropped"); undecodable images are listed separately. The entry is written before its images finish encoding, so a crash cannot lose the prompt; "still saving" shows until encoding lands, and entries orphaned by a reload are settled on load.
  - Files are not stored as bytes: the entry keeps the signed-upload reference. Stashing refuses while uploads are unfinished ("Wait for file uploads before stashing this prompt") or files need reattaching. On restore each file is verified with the server; uploads expire after 24 hours unclaimed, and expired files are reported ("stashed files are kept for 24 hours and this upload expired. Attach the file again."). Files from another environment cannot be restored there ("Stashed files belong to another environment").
  - Restore appends to existing composer text rather than replacing it; an image-only entry adds no blank lines.
  - When browser storage is unavailable the stash works in memory and warns ("Stashed prompt will not survive a reload"); a non-durable take warns that the entry may come back.
  - Persistence: localStorage key `e6code:prompt-stash:v2`, schema version 2. The legacy key `e6code:prompt-stash:v1` (per-provider queues with model selection) is deleted at startup, not migrated. Shares the ~5 MB origin quota with composer drafts (E14-T06).
- **Surfaces:** web and desktop only. Mobile has no stash (not found in report 09).
- **Where the code lives:** `apps/web/src/promptStashStore.ts` (302), `components/chat/ComposerStashMenu.tsx` (227), `ComposerStashBadge.tsx` (66), `ChatComposer.tsx:4159-4720` (stash, restore and delete handlers).

## Problems today

- About 560 lines of stash handling live inside `ChatComposer.tsx`.
- Base64 images in localStorage compete with drafts for the same small quota.
- The stash is per browser: a prompt stashed on desktop is not available on the hosted web app or mobile.

## Remodel goals

- **Experience:** the stash is a compact mark in the composer footer with a tooltip and count (design direction §8 Composer); the drawer is a floating list with clear per-entry warnings (dropped images, expired files) in words.
- **Motion:** stashing is a user-caused move: the prompt block travels into the stash mark (`matchCut`) or cuts; restore reverses it. The badge's acknowledgement uses `numberChange` on the count, not a repeating pulse.
- **Performance:** no image bytes in localStorage in v2; reuse the attachment representation from E14-T06 and keep the 20-entry cap.
