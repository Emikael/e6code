# E14-T09 · Composer footer, resting mode and banner stack

## What it is

The composer's footer holds the controls around the prompt: the "+" attach button, model chip, traits and effort, permissions chip, plan toggle, context meter, stash badge, and the primary action (Send or Stop). Below it sits the context strip (workspace mode, PR, branch; owned by E23-T01). Above the composer sits the **banner stack**: notices about the thread or environment (offline, reconnecting, version mismatch, branch mismatch, snoozed or settled, woke from snooze, resume after compaction, usage limits, project clone progress, Codex feedback upload, handoff, auto-balance updates). This task owns the footer layout, its compact and **resting** modes (the composer collapses to a single line when the user scrolls up in an existing thread), and the banner stack container and ordering.

## When it is used

- Always: every composer shows a footer; narrow windows use the compact layout.
- Reading back through a long thread: the composer rests as one line so the conversation gets the space.
- Whenever the thread or environment is in a state the user should know about before sending.

## How it works today

- **Entry points:** the footer controls themselves; the overflow "…" (`CompactComposerControlsMenu`) gathers controls that do not fit; banners carry their own actions (Reconnect, Disconnect, Restore branch, Un-settle, Wake, Continue in new thread, Copy ID, Update).
- **Behaviour to preserve:**
  - Compact footer thresholds at 620 px and 780 px of composer width (`composerFooterLayout.ts`); controls that do not fit move into the overflow menu; image thumbnails show three plus a count.
  - Resting mode on existing threads when scrolled away: a collapsed single line with overlaid actions; it expands on focus or typing; paste into a blurred resting composer is redirected into it. Placement measured by `restingComposerControlsMeasurement.ts` and resize observers.
  - Permissions has exactly one visible home (`resolveRuntimeModeDisplay`): a labelled chip when the thread differs from the default, inside the effort menu when the model has one, else an icon-only chip (E15-T08).
  - The primary action is Send, or Stop while a turn runs (E15-T05); disabled states carry a reason.
  - Banner stack: items assembled in `ChatView.tsx` by ordered array concatenation with two tiers (`activity` and `notice`); several stacked at once; each dismissible where it makes sense. Banner producers belong to other tasks (environment availability and version skew E13-T16, branch mismatch E23-T08, snooze/settle E09-T03, usage limits and handoff E15-T04, compaction E15-T03, feedback E15-T07, update notices E12-T05, clone progress E11-T04, auto-balance E29-T08); this task owns the container, order and choreography.
- **Surfaces:** web and desktop. Mobile has its own toolbar (`ComposerToolbar.tsx`, E32-T03).
- **Where the code lives:** `apps/web/src/components/chat/composerFooterLayout.ts`, `restingComposerControlsMeasurement.ts`, `CompactComposerControlsMenu.tsx`, `ComposerControl.tsx`, `ComposerSurface.tsx`, `useComposerMultilinePrompt.ts`, `ComposerBannerStack.tsx` (378), `ComposerBanner.tsx` (367), `ChatView.tsx:6949` (banner assembly), `useAutoBalanceUpdateBanner.tsx`.

## Problems today

- Layout depends on measurement (resize observers, measured control placement), which is fragile and costs layout work.
- Banner priority is partly implicit in array order inside ChatView; nothing guarantees the most important notice is on top.
- Notices compete: banners above the composer, overlays above the timeline, and the frontier card can all show at once (design direction §1).

## Remodel goals

- **Experience:** footer controls become compact marks with tooltips (model as provider mark plus "Model · effort"; context meter, permissions and stash as small marks), per design direction §8 Composer. Banners follow one priority list (blocking states first: environment offline, then decisions, then informational), show at most two at once with "N more", and always pair status with a word or icon.
- **Motion:** a banner entering uses `reveal`; the composer's height change uses the `layout` preset once (never animating `height`); resting ↔ expanded is a `layout` change triggered by the user (focus, typing), never by streaming content; dismiss within 140 ms.
- **Performance:** container queries or CSS layout instead of JS measurement for compact thresholds where possible; nothing in the footer re-renders on streamed events.

## Done when

- [ ] Footer parity at full, 780 px, 620 px and 360 px widths, with every control reachable (overflow menu by keyboard).
- [ ] Resting mode parity: collapses on scroll-away, expands on focus, typing and paste.
- [ ] Banner stack has an explicit, tested priority order and a cap; every producer listed above plugs into it.
- [ ] Dark and light reviewed; reduced motion gives instant height changes.
- [ ] Banner choreography shared with update notices (E12-T05), not duplicated.
