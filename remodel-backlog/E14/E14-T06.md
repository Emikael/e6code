# E14-T06 · Composer drafts persistence

## What it is

Whatever a user has typed or attached in a composer is kept as a **draft**, per thread and per unsent new-thread draft, and survives switching threads, closing the tab and restarting the app. A draft holds the prompt, images, files, terminal contexts, preview annotations, review comments, model selection per provider, runtime and interaction modes, and, for new-thread drafts, the project, environment, workspace mode and branch. The store also tracks draft sessions while they are promoted into real threads. It is the one piece of composer state already saved in users' browsers, so the rewrite must read it.

## When it is used

- Switching away from a half-written prompt and coming back.
- Reloading the browser or relaunching the desktop app mid-prompt.
- Opening the app to find a new-thread draft still waiting in the sidebar.
- Answering an agent question with attachments (question attachments are stored as drafts too).

## Current screen

No screenshot: persistence has no UI. Its visible effects are restored prompts, thumbnails, and "needs reattach" rows for files whose upload did not survive.

## How it works today

- **Entry points:** every edit in the composer; hydration at app start; draft promotion on first send; thread delete and archive (draft cleanup); question-attachment drafts keyed by `questionAttachmentDraftId(environment, thread, request, question)`.
- **Behaviour to preserve:**
  - **Storage:** zustand `persist` under localStorage key `e6code:composer-drafts:v1` with internal schema `version: 9` (`COMPOSER_DRAFT_STORAGE_VERSION`). Writes go through a deferred storage with a 300 ms debounce (`createDeferredStorage`) and are flushed on `beforeunload`. Falls back to in-memory storage when localStorage is unavailable.
  - **Migration:** `migratePersistedComposerDraftStoreState` normalises any persisted shape from `unknown`: legacy and v2 drafts (single `provider`/`model`/`modelOptions`, legacy Codex fields) are converted to v3 `modelSelectionByProvider` + `activeProvider` + `modelSelectionExplicit`; old `e6-context://v1/<kind>/<producer-id>` links are rewritten to kind-scoped context IDs; legacy terminal placeholders are migrated (`migrateLegacyTerminalContextPlaceholders`); model seeds are stripped from empty draft sessions.
  - **What is persisted per thread key** (`partializeComposerDraftStoreState`): `prompt`; `attachments` = images as full base64 `dataUrl` with id, name, MIME type, size and optional SnapShot source; `files` = metadata markers with `attachmentId` and `environmentId` when the signed upload finished, otherwise metadata only so the file returns as a needs-reattach row; `terminalContexts`; `previewAnnotations`; `reviewComments`; `modelSelectionByProvider`, `activeProvider`, `modelSelectionExplicit`; `runtimeMode`; `interactionMode`. Empty drafts are not written.
  - **Draft sessions** (`draftThreadsByThreadKey`): project, environment, `logicalProjectKey`, `environmentSelection` (`auto`/`manual`, for load balancing) and `loadBalancedEnvironmentId`, `createdAt`, env mode, `branch`, `worktreePath`, `startFromOrigin`, `promotedTo` (the server thread a draft became). A session is kept only if it is mapped to a project's "new thread" slot, is mid-promotion, or holds user content; zombie sessions and their composer blobs are dropped on write.
  - Hydration verifies persisted image attachments against storage and restores them; background-submission tracking and effective model state are derived from the store.
  - The store is shared with the sidebar (draft rows), the new-thread flow (E13-T01) and the question panel (E16-T03).
- **Surfaces:** web and desktop. Mobile persists drafts separately (`state/use-composer-drafts.ts`, sqlite client cache, E32-T03). Server: none.
- **Where the code lives:** `apps/web/src/composerDraftStore.ts` (4,303 lines; test file 3,405 lines), `lib/composerDraftUploads.ts`, `chat/pendingDraftWork.ts`, `lib/storage.ts`, `questionAttachments.ts`.

## Problems today

- 4.3k lines mixing persistence, migration, draft-session lifecycle, model resolution and attachment bookkeeping.
- Base64 images in localStorage: a single blob for all threads, rewritten on every change after debounce, sharing a ~5 MB origin quota with the prompt stash (`e6code:prompt-stash:v2`). Architecture §2.3 and §3.2 item 13 ask for per-key persistence in IndexedDB with no attachment bytes in the store.
- The key name says `v1` while the schema is version 9; readers must check both.

## Remodel goals

- **Experience:** a draft never disappears: after any reload the prompt, chips and attachments come back, and anything that cannot come back is listed with a Reattach action.
- **Performance:** per-thread-key records in IndexedDB through the deferred-write helper; a keystroke writes only its own thread's record; no base64 bytes in UI state (attachments referenced by signed-upload ID or a local Blob handle). Define a persistence budget (maximum bytes per draft, maximum total) and measure write cost per keystroke in the harness.

## Done when

- [ ] A written persistence and migration plan approved by the maintainer: v2 reads `e6code:composer-drafts:v1` (every schema version the current `migrate` accepts, fixtures for v2, v3 and v9 shapes) once, imports each thread's draft into the new per-key store, and removes the old key only after the import is verified. Images stored as base64 are converted to the new attachment representation on import.
- [ ] Old clients and new clients do not corrupt each other if a user switches the v2 flag off again (flag rollback keeps or re-exports the legacy key until the legacy composer is deleted).
- [ ] Draft sessions keep promotion state, environment selection and branch across reloads; zombie cleanup rules preserved.
- [ ] Question-attachment drafts and stash interplay (shared quota) covered.
- [ ] Persistence budget defined and measured; unit tests ported from `composerDraftStore.test.ts` for migration and partialize rules.
- [ ] v2 code does not import `composerDraftStore` (architecture §2.2 rule); shared logic extracted to `next/features/composer/model` or `client-runtime`.

+++ Agent notes

- Inventory sources: `02:F-25`.
- Rewrite size: XL. Persisted user data with nine schema versions, shared by several features; mistakes lose users' work.
- Traps: `persist` version check (`persisted.version !== 9`) is used when reading attachment IDs directly from storage. Migration must stay idempotent (it runs on every load). Draft keys for question attachments are JSON-encoded and URI-encoded; keep the format or migrate it. `beforeunload` flush is the only guard against losing the last 300 ms of typing; IndexedDB writes are async, so design an equivalent (for example `visibilitychange` flush). Load balancing reads `environmentSelection`. Multi-tab: two tabs writing the same blob today is last-writer-wins; per-key storage should not make it worse.
