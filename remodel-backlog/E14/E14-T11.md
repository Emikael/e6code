# E14-T11 · Voice input on web and desktop

## What it is

A decision: should the web and desktop composer get voice input (dictation)? Today only the iPhone app has it: a microphone control records up to five minutes and transcribes on-device with Apple speech (iOS 26 and later), using a recording state machine shared in `@e6tools/client-runtime/voice-input`. The web client has no dictation code at all.

## When it is used

- Describing a long task faster than typing it, especially on a tablet or laptop away from a desk.
- Accessibility: users who cannot type comfortably.

## Current screen

No screenshot: there is no web or desktop UI. Mobile has a dictation control with a waveform strip, cancel and confirm (not captured; no simulator in the capture environment).

## How it works today

- **Entry points:** mobile composer microphone button only.
- **Behaviour to preserve (mobile, for reference):** recording with metering waveform, keep-awake and audio-session handling, cancel and confirm, transcription inserted into the composer, recording/transcribing/error states; limit about five minutes; on-device transcription on iOS via `@react-native-ai/apple`. Android transcription path not verified.
- **Surfaces:** mobile (iOS) only. Web and desktop: none. Server: none (transcription is on-device).
- **Where the code lives:** `apps/mobile/src/voice-input/*` (`ComposerDictationControl.tsx`, 419 lines), `native/voiceTranscription*.ts`, `packages/client-runtime/src/voice-input`.

## Problems today

- The capability differs across surfaces with no recorded decision.

## Remodel goals

- **Experience:** if adopted, voice input is a control in the composer footer that turns the composer into a "recording" state (the fifth state of the slate), with a static level meter, cancel and confirm; text lands in the editor for review before sending.
- **Performance:** any speech engine must load lazily, never on the chat critical path (bundle budget: entry plus chat route ≤ 350 KB brotli).

## Done when

- [ ] The maintainer records a decision for web and desktop: none, browser Web Speech API (with its privacy caveat that some browsers send audio to a cloud service), OS dictation only, or a local model.
- [ ] If yes: a follow-up task is filed with the engine, privacy statement for user docs, and reuse of the shared `voice-input` state machine.
- [ ] If no: user docs state that dictation is available on iPhone only.
