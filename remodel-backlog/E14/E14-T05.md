# E14-T05 · Send pipeline

## What it is

The send pipeline is everything that happens between the user pressing Send and the agent receiving the turn: validating the draft, showing the user's message immediately (optimistic), finishing attachment uploads, creating a worktree for a new thread, choosing provider, model, options and modes, dispatching the `thread.turn.start` command to the server, and putting everything back in the composer if any step fails. Today it is one ~1,300-line function (`onSend`) inside `ChatView.tsx`. It has no screen of its own, but every composer, plan, queue and handoff feature calls it.

## When it is used

- Enter or the Send button in any thread or draft.
- A queued message leaving at a tool boundary or via "Send now" (E15-T05).
- "Implement plan" and plan refinements (E16-T04), compaction (`/compact`, E15-T03), preview annotations sent directly from the browser panel, multi-model fan-out from a draft (E15-T01).
- Cmd/Ctrl+Enter on a draft: start the thread in the background and open a fresh draft.

## Current screen

The pipeline has no UI of its own. Its visible results are the optimistic user bubble, the running state and error banners (E13-T16).

## How it works today

- **Entry points:** Enter / Mod+Enter per Settings → General → Send shortcut; Send button; Cmd/Ctrl+Enter on a draft ("Start in background"); Mod+Enter while running (the "alternate" intent, opposite of the Follow-up behaviour setting); queued-message release; plan follow-up buttons; preview annotation direct send. Submission intents in code: `foreground`, `background`, `alternate`.
- **Behaviour to preserve:**
  - Validation first: prompt length (E14-T08), provider input validation (`validateProviderInput`), attachment limits, "Choose a project first" when a draft lost its project, branch required in New worktree mode ("Select a base branch before sending in New worktree mode."), Antigravity-specific send-block reasons, provider not ready, environment unavailable (send disabled with a toast after a 2 s grace, E13-T16).
  - While a turn runs, a send is queued instead when Follow-up behaviour is "Queue" (and steers immediately when "Steer"); Mod+Enter flips it for one message (E15-T05).
  - Local commands are intercepted: `/usage-limits` (notice, no turn), `/plan` and `/default` (mode switch), provider-native commands sent verbatim.
  - Optimistic user message, then attachment uploads with progress; images are cloned for retry.
  - First message of a draft: create the thread, create and prepare the worktree when in worktree mode, set the branch, auto-title from the first message (title generation itself is E13-T17), then promote the draft route without remount (E13-T01).
  - Dispatch carries provider instance, model, model options (effort and traits), runtime (permission) mode and interaction (plan) mode. Claude "ultrathink" effort is injected as a prompt prefix (`applyClaudePromptEffortPrefix`).
  - Expired terminal contexts are dropped with a toast; review comments and annotations are appended as blocks.
  - On any failure the composer is restored from snapshots (prompt, images, files, terminal contexts, annotations, review comments) and the error shows on the thread.
  - Races: a Stop during a queued message's upload must not start a new turn (`drainGeneration`); `sendInFlightRef` prevents double sends; the draft hero docking waits for the transition.
  - Server: commands are acknowledged when the intent is committed (event log and receipts in one transaction); the server's command gate queues commands until it is ready. Optional Jev routing may answer the turn before it reaches the provider (E15-T06).
- **Surfaces:** web and desktop. Mobile has its own send path with an offline outbox and drain worker (E32-T03). Server: `thread.turn.start` through the decider and `ProviderCommandReactor`.
- **Where the code lives:** `apps/web/src/components/ChatView.tsx:7765-9100` (`onSend`), `ChatView.logic.ts` (`deriveComposerSendState`, `buildLocalDraftThread`, `resolveSendEnvMode`), `chat/composerSubmission.ts`, `lib/attachmentUploadQueue.ts`, `queuedMessageStore.ts`.

## Problems today

- About 1,300 lines in one closure inside an 11,255-line component, with many failure and rollback paths and no direct tests.
- Gates are scattered (environment, settings hydration, checkpoint rewinding, detail loading, load balancing, provider status) and re-checked separately by the queue.
- Special cases for providers and commands are inline string checks.

## Remodel goals

- **Experience:** sending never loses what the user wrote: every failure returns the full draft and says why in one place. The user's message appears instantly (optimistic) on local and remote connections.
- **Motion:** the send press uses the `press` preset; the first send runs set-piece 3.2 (owned with E13-T01 and E14-T01). Server confirmation never gates the motion (architecture §4.1 rule 6).
- **Performance:** the pipeline is a pure, testable module outside React (`next/features/composer/model` or `client-runtime`), so a send does not re-render the timeline. Wait on command receipts, never sleeps or polling (AGENTS.md).

## Done when

- [ ] `onSend` is replaced by a send module with explicit stages (validate, intercept, snapshot, upload, create/prepare, dispatch, restore) and unit tests for each failure path.
- [ ] Every entry point and intent above is covered, including background start on drafts and multi-model fan-out.
- [ ] Restore-on-failure verified for each attachment and context kind.
- [ ] Stop-versus-queued-upload race and double-send guards have tests.
- [ ] Optimistic message and composer clearing measured: keystroke-to-paint and send-to-bubble under the remote profile (60 ms RTT).
- [ ] E15 and E16 tasks consume this module rather than calling ChatView.
