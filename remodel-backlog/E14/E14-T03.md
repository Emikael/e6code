# E14-T03 · Attachments: drop, paste and upload

## What it is

Users attach images, videos, files and folders to a message by dropping them on the chat column, pasting them, or picking them from the composer's "+" button. Images show as thumbnails above the prompt; files show as chips. Uploads start as soon as a file is added, through a short-lived signed upload URL on the environment server, so sending does not wait for bytes to travel. A very long paste (32 KiB or more) becomes a text-file attachment. Folders dropped in the desktop app become `@` path mentions instead of uploads.

## When it is used

- Showing the agent a screenshot of a bug or a design to match.
- Giving the agent a log, CSV, PDF or spec file that is not in the workspace.
- Pasting a huge stack trace without flooding the prompt.
- Dropping a folder from Finder to point the agent at it (desktop).

## How it works today

- **Entry points:** drag over the chat column (overlay "Drop files to attach"); paste (Cmd/Ctrl+V) in the composer or with nothing focused; "+" button (file picker); drop onto a sidebar thread row to attach to that thread's composer (owned by E09-T04); SnapShot capture (E22-T04) and element annotations (E21-T05) arrive as attachments or context; re-attach rows for files restored from a draft.
- **Behaviour to preserve:**
  - Limits (contracts `orchestration.ts`): up to 100 attachments per message (`PROVIDER_SEND_TURN_MAX_ATTACHMENTS`), images ≤ 10 MiB each and ≤ 80 MiB total, other files ≤ 50 MiB. Antigravity is stricter: 1 MiB per text file, 10 MiB per image, 20 MiB per audio clip, 50 MiB per message. Over-limit adds are refused with a message, not silently dropped.
  - Images: PNG, JPEG, GIF, WebP; compressed client-side (`lib/imageCompression.ts`); HEIC/HEIF converted to JPEG. Videos get a first-frame thumbnail (`lib/videoFirstFrame.ts`). Thumbnail strip shows three and an overflow count in compact layouts.
  - Text paste ≥ 32 KiB (`PASTED_TEXT_ATTACHMENT_THRESHOLD_BYTES`) becomes a text-file attachment; Cmd/Ctrl+Shift+V keeps it editable.
  - Upload flow: `attachments.createUploadUrl` returns a token valid 10 minutes; the client POSTs the bytes to `/api/attachments/upload/<token>` (content length must match), the server stores a pending attachment that the first message claims. Upload progress is shown per item (`lib/attachmentUploadQueue.ts`, `attachmentUploadState.ts`); removing an item deletes the pending upload (`attachments.delete`). A legacy path still accepts inline base64 `dataUrl` inside `thread.turn.start`.
  - Server side: `Normalizer.ts` enforces limits and moves pending uploads into the thread; a sweeper removes unclaimed pending uploads after 24 hours and partial files after 1 hour; revert and thread delete prune attachments.
  - Viewing attachments uses short-lived signed asset URLs (`assets.createUrl`, 1 hour; `GET /api/assets/<token>/<path>` with Range support, content type from extension only, `nosniff`).
  - Files in the composer are tied to the environment that holds their upload; a file whose upload was lost (reload before finish, expired) shows as a "needs reattach" row instead of vanishing.
  - Folder drop in Electron becomes a project path mention (`folderDrop.ts`); in the browser a folder cannot be read.
  - Send waits for uploads still in flight; Stop racing a queued message's upload is guarded (`drainGeneration`, E15-T05).
  - Per-provider: Codex, Claude, Cursor, Grok and Antigravity take images natively (Claude only for supported MIME types); other files are passed as environment-local paths except Antigravity, which takes images, PDFs, text and audio natively; OpenCode image handling not verified (E37-T11).
- **Surfaces:** web and desktop (desktop adds folder drop). Mobile has its own picker (photo library, camera, documents), share sheet and offline outbox (E32-T03, E35). Server: `apps/server/src/attachmentStore.ts`, `attachmentPaths.ts`, `assets/AttachmentUpload.ts`, `assets/AssetAccess.ts` (862), `orchestration/Normalizer.ts`, `imageMime.ts`; contracts `orchestration.ts`, `assets.ts`.
- **Where the code lives:** `apps/web/src/components/chat/composerAttachmentFiles.ts`, `workspaceFileDrop.ts`, `folderDrop.ts`, `ComposerImageThumbnail.tsx`, `SnapShotAttachmentDetails.tsx`, `lib/attachmentUploadQueue.ts`, `lib/attachmentUploadState.ts`, `lib/composerDraftUploads.ts`, `ChatView.tsx:10405` (drop overlay).

## Problems today

- Draft images are persisted as base64 data URLs in localStorage (shared ~5 MB origin quota with the prompt stash); architecture §2.3 asks v2 stores to keep bytes out of the store.
- The inline base64 path in `thread.turn.start` is the largest single RPC payload class on the server.
- Path-traversal checks are hand-rolled in `attachmentPaths.ts` (security-sensitive).
- The drop overlay is inline JSX inside `ChatView.tsx`.

## Remodel goals

- **Experience:** the attachments strip is part of the composer's "writing" state: it grows above the editor, each item shows progress, failure with Retry/Remove, and a clear reason when a limit is hit (including the provider-specific Antigravity limits). The drop overlay is a quiet `--plane-well` target with one sentence.
- **Motion:** the strip's height change uses the `layout` preset once; thumbnails appear with `reveal`; drag follows the pointer 1:1 and only the drop settles (§3.10).
- **Performance:** no attachment bytes in persisted UI state; upload and compression never run on the input path. Keep the inline-dataUrl path for old clients but do not use it from v2; name the PR-blocking WebSocket payload gate (no live frame > 256 KiB) and the existing "Thread transfer impact" CI check as guards.
