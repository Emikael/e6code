# E23-T11 · Project actions: run, edit, import from e6.json

## What it is

**Project actions** (called "project scripts" in code) are named shell commands saved per project, such as "Dev server", "Test" or "Lint", that run with one click from the chat header in the thread's terminal. Each action has a name, an icon, a command, an optional keybinding and options such as running automatically when a new worktree is created (a **setup script**) or opening a preview URL. Actions can also be checked into the repository in a project file, `e6.json`, and imported from there.

## When it is used

- Starting the dev server or running tests for the code the agent just changed, without typing in the terminal.
- New worktrees need dependencies installed: the setup script runs automatically (progress card in E13-T12).
- A team shares its standard commands through `e6.json` in the repository.

The editor dialog has Name, an icon picker (about 8 icons), Keybinding ("Press shortcut" capture), Command, Preview URL (optional), switches "Run on worktree create", "Wait for setup" (setup scripts only) and "Auto-open preview", and footer Delete, Cancel, Save; Delete asks for confirmation.

## How it works today

- **Entry points:** the "Run <action>" item and "Project actions" submenu in the header overflow menu; keybindings `script.<id>.run` (one per action); Settings → project → Actions (`ProjectActionsSettings.tsx`, `ProjectActionsList.tsx`, E25-T07); the editor dialog from Add action, the pencil, or Settings; mobile terminal menu lists project scripts (E33-T04). Related: `chat.new` (may ask for a project) and `chat.newLocal` (skips the chooser) keybindings, documented next to script bindings.
- **Behaviour to preserve:**
  - Fields: id, name, icon, command, keybinding, `runOnWorktreeCreate`, wait-for-setup (`async` in `e6.json`), `previewUrl`, `autoOpenPreview` (only meaningful with a preview URL).
  - Primary action chosen by `preferredScriptId`.
  - Running: opens the thread's terminal drawer, reuses the active terminal unless it is busy (then opens a new one), sets the cwd to the thread's worktree or project root, and injects runtime environment variables (`projectScriptRuntimeEnv`). Failure sets a thread error "Failed to run script "X"."
  - Running the setup script in a thread that has a worktree asks the server to re-run worktree setup (`worktreeSetupRerun`) so the exit code is tracked; older servers fall back to a plain terminal run.
  - The editor writes the keybinding to server keybinding config and validates conflicts and failed imports.
  - `e6.json` (schema `https://e6code.com/schema/e6.json`): `iconPath`, `defaultThreadEnvMode`, `scripts[]`. Missing or invalid files are treated as absent. Settings flags drift between environments and invalid files.
  - Actions are stored per project with per-checkout overrides (`projectScriptOverrides` in server settings).
- **Surfaces:** web and desktop (header and Settings, two layouts); mobile runs scripts from the terminal menu but has no editor (not verified beyond report 09); server: `E6ProjectFileLoader.ts`, settings, setup runner.
- **Where the code lives:** `apps/web/src/components/ProjectScriptsControl.tsx` (375), `projectScriptEditor.tsx` (481), `projectScripts.ts`, `lib/projectScriptKeybindings.ts`, `hooks/useE6ProjectFileScripts.ts`, `components/settings/ProjectActionsList.tsx`, `ProjectActionsSettings.tsx`, `useProjectScriptSettings.ts`; run logic `ChatView.tsx:4414+`; server `project/E6ProjectFileLoader.ts` (118), `packages/contracts/src/e6ProjectFile.ts`, `project/ProjectSetupScriptRunner.ts`.

## Problems today

- Two different layouts for the same list (header menu vs Settings), and a third, unused toolbar layout in code.
- The one-click run is hidden inside the overflow menu.
- Run logic lives in ChatView.
- Users cannot see whether an action is already running or whether it exited with an error from the header; they must open the terminal.
- Inventory mismatch: report 04 names the keybinding `projectScript.<id>`; the code (`projectScripts.ts:54`) and docs use `script.<id>.run`.

## Remodel goals

- **Experience:** one action list component for header and Settings; a visible Run control shows running state (icon plus word, e.g. "Running") and last exit status; importing from `e6.json` is one click with a preview of what will be added.
- **Motion:** Run press uses `press`; a running action shows the live mark only while its process runs (finite, stops when it exits).
- **Performance:** reading `e6.json` stays lazy and cached per project.
