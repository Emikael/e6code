# E23-T07 · Initialize Git and publish repository

## What it is

Two ways to bring a project under source control from the thread header. **Initialize Git** runs `git init` in a project that is not a repository yet. **Publish repository** is a three-step wizard that creates a new hosted repository on GitHub, GitLab, Bitbucket, Azure DevOps or Forgejo/Gitea, adds it as a remote (normally `origin`) and pushes the local commits.

## When it is used

- A user started a project from an empty folder or a scratch directory and now wants version control.
- A local repository has commits but no remote, and the user wants to share it or open PRs.

In words: for a non-repository, the Git actions control shows an "Initialize Git" button. With a repository but no remote, the quick action reads "Publish repository" and the menu has "Publish repository...". The wizard dialog ("Publish repository", "Pick where to host it, then point us at a repo to push to.") has a step header Provider → Repository → Summary. Step 1 lists providers with their icons; providers that are not installed or signed in are disabled with the hint "Open Settings -> Source Control to configure this provider." Step 2 takes the repository path (`owner/name`), visibility (Private "Only invited people" / Public "Anyone on the web") and, under Advanced, the remote name (default `origin`) and protocol (SSH default, or HTTPS). Step 3 shows "Repository published" (or "Repository created" with `Remote "origin" is set up. Make a commit and push it to share your code.`) with an open link, or "Publish failed".

## How it works today

- **Entry points:** Git actions quick action and menu (E23-T04); `useVcsInitAction` (`vcsInit` RPC); `useSourceControlPublishRepositoryAction` (`sourceControlPublishRepository` RPC); provider readiness from `serverDiscoverSourceControl`.
- **Behaviour to preserve:**
  - Provider readiness: each provider is gated by CLI installed and authenticated (discovery), with the Settings hint; Settings → Source Control has Rescan (E25-T08).
  - Repository path must have both an owner and a name to continue.
  - Created-but-empty repo vs pushed repo produce different result copy.
  - Back/Cancel navigation; steps cannot be skipped forward; on the result step the header is locked.
  - Closing resets the form (remote back to `origin`, step 0, Advanced closed).
- **Per host (create repository):** all five implement `createRepository`.
  - GitHub: `gh repo create` through `GitHubCli.ts`; needs `gh` 2.81.0+ and `gh auth login`.
  - GitLab: `glab`, `glab auth login`.
  - Bitbucket: REST API with `E6CODE_BITBUCKET_ACCESS_TOKEN`, or `E6CODE_BITBUCKET_EMAIL` plus `E6CODE_BITBUCKET_API_TOKEN`; server restart needed after changing them.
  - Azure DevOps: `az` with the azure-devops extension, `az login`.
  - Forgejo/Gitea: `fj --host <server> auth add-token` or `tea login add` (tea 0.16+).
- **Surfaces:** web and desktop. Mobile: not found in the mobile inventory (report 09 lists repository options in the git sheet; publish not verified). Server: `SourceControlRepositoryService.ts` (461), provider CLIs.
- **Where the code lives:** `apps/web/src/components/GitActionsControl.tsx:420–~956` (`PublishRepositoryDialog`), `state/sourceControlActions.ts:260`, `state/sourceControl.ts`; server `sourceControl/SourceControlRepositoryService.ts`, `SourceControlProviderDiscovery.ts`, `*Cli.ts`, `BitbucketApi.ts`.

## Problems today

- The wizard is ~540 lines embedded in the Git actions file; it deserves its own component.
- Steps are hidden with CSS rather than unmounted, so all three stay rendered.
- The provider hint points at Settings in text only, with no link.

## Remodel goals

- **Experience:** a short, confident flow: suggested repository name from the folder, owner prefilled from the signed-in account, provider readiness shown with a direct link to fix it in Settings → Source Control.
- **Motion:** step changes use `sideBySide` (direction by depth); success lands with `checkDraw`. Reduced: fades only.
