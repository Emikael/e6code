# E25-T01 · Settings shell, navigation and search

## What it is

The frame every settings page lives in: the settings navigation in the sidebar, the page header with the scope selector, the page title and description, the "Search settings" box that finds an individual setting by name and scrolls to it, and the shared row primitives (label, description, control, reset button, inheritance marker) that every settings page is built from. It is the equipment rack the other M5 epics (Theming, Providers, Usage, Connections) plug their pages into.

## When it is used

- Opening Settings from the nav rail, the sidebar footer, the command palette ("Settings", "About"), or the desktop menu **Settings…** (Cmd/Ctrl+,).
- Looking for one setting without knowing which page owns it ("send shortcut", "worktree", "mod+b").
- Following a deep link from elsewhere in the app that lands on a specific row (for example `/settings/general#about-version` from the "Check for updates" palette command, `/settings/source-control` from a git error, `/settings/connections` from a connection notice).
- Moving between pages, then pressing Esc to go back to where you were.

_Settings shell in light appearance_

Today the settings route reuses the app sidebar in a "settings mode": a **Search settings** field at the top (focus with `/`), then four groups of pages: **App** (General, Appearance, Keybindings, SnapShots), **Agents** (Providers, Integrations), **Projects** (Project, Source Control), **Environment** (Connections, Storage, Archive). Providers shows an "N signed out" badge, Connections a saved-environment count. Diagnostics and Open source licenses are detail pages reached from General and shown under its heading. The right side is a page header (scope breadcrumb on the left, "Restore device defaults" on the right on General only), then the page: title, one-line description, and sections of rows.

## How it works today

- **Entry points:** nav rail Settings item (`AppNavRail.tsx`), sidebar chrome button (`SidebarChrome.tsx`), command palette navigation to `/settings`, `/settings/general#about-version`, `/settings/source-control`, `/settings/connections` (`CommandPalette.tsx`), desktop application menu "Settings…" with CmdOrCtrl+, (`apps/desktop/src/window/DesktopApplicationMenu.ts`). `/settings` redirects to `/settings/general`; an unauthenticated client goes to `/pair` (the hosted static app is allowed in). Settings search: `/` focuses it; results navigate to `<page>#<anchor>`. There is **no keybinding command** for opening Settings in `packages/contracts/src/keybindings.ts`; only the desktop menu accelerator exists.
- **Behaviour to preserve:**
  - Routes: 13 child routes (`general`, `appearance`, `keybindings`, `snap-shot`, `providers`, `integrations`, `projects`, `source-control`, `storage`, `connections`, `archived`, `diagnostics`, `open-source-licenses`). Each route file only mounts a panel.
  - Page header: `Settings / <group>` breadcrumb, title and description from `settingsNavGroups.ts` (for example Storage: "How long worktrees, artifacts, and logs are kept.").
  - "Device only" pages (Appearance, SnapShots, Connections) hide the scope selector; the Project page only appears in the nav when a project is selected in the scope (see E25-T02).
  - Esc: an open dialog or popup handles its own Esc; a focused text field is blurred first; a second Esc leaves Settings back to the previous app route (`settingsEscapeAction`, `useSettingsBackNavigation`, `settingsBackDestination.ts`).
  - Shell notices: "Reconnect X to change its settings" when the selected environment is disconnected; the scope's own "unavailable" message (stale project, environment or checkout); "<Setting> is not available for the selected target. Choose its owning scope to continue." with a picker when a search result needs another scope; "<Setting> requires a supporting environment…" when a result needs thread auto-settlement support.
  - Search: matches normalised title, section name, and remembered terms (descriptions, option labels, aliases); multiple words match across fields and the strongest result ranks first; empty query returns nothing; "No results" state. Keybinding commands are included (one result per command, findable by label, command id or default key such as `mod+b`) but always rank after real settings. A command with no default key points at the Keybindings section instead of a row.
  - Availability filtering: results whose row would not render are hidden: `desktopOnly`, `macOnly`, `windowsOnly`, `cloudOnly` (E6 Connect configured), `environmentOnly`, `providerSettingsOnly`, `localBackendManagementOnly`, `localEnvironmentOnly`, `wslAvailableOnly`, `requiresThreadAutoSettlement`. Each result also carries the scope it needs (`environment`, `environment-defaults`, `project-defaults`, `project`, `checkout`, `connections`); device rows need none.
  - Landing: selecting a result navigates, scrolls the row into view and highlights it once (`useSettingsSearchTarget`, `scrollToSettingsTarget` in `settingsLayout.tsx`); the Keybindings page clears its own filter when it is the target.
  - Layout primitives (`settingsLayout.tsx`, 591 lines): `SettingsPageContainer`, `SettingsSection`, `SettingsRow` (title, description, status line, control, `serverScoped` marker, `settingKeys`, `mixed`), `SettingResetButton` (per-row reset to default), `SettingsUnavailableGroup` ("Only available in the desktop app"), `SettingsPageNotice`, `FoldedSettingsSection`, `ScopedSwitch`, `SettingsGroup`, `SettingInheritance` (the layers popover, see E25-T02), a relative-time tick for "Checked 2 min ago" style labels.
- **Surfaces:** web and desktop share this shell. Mobile has its own settings index (`apps/mobile/src/features/settings/SettingsRouteScreen.tsx`, sections Connections, Interface, Projects & threads, Server settings, App) with an environment filter in the header; it is rebuilt in E34-T05 and has no settings search.
- **Where the code lives:** `apps/web/src/routes/settings.tsx` (216), `routes/settings.*.tsx`, `components/settings/SettingsSidebarNav.tsx` (439), `settingsNavGroups.ts` (176), `settingsSearch.ts` (1,027), `settingsSearch.test.ts`, `useAvailableSettingsSearchItems.ts`, `settingsLayout.tsx` (591), `SettingInheritance.tsx` (301), `FoldedSettingsSection.tsx`, `ScopedSwitch.tsx`, `SettingsGroup.tsx`, `settingsBackDestination.ts`.

## Problems today

- **The search index is a hand-maintained parallel list.** `SETTINGS_SEARCH_ITEMS` holds about 110 hand-written entries (title, page, anchor, search terms, availability flags, required scope) plus one generated entry per keybinding command. Rows that call `searchableSetting(id)` take their anchor id and title from the catalog, so those cannot drift, but a new row that does not call it is simply unsearchable, and availability flags must be kept in step with the conditions that hide the row by hand.
- The whole page subtree is remounted on every scope change and after "Restore device defaults" (`key={JSON.stringify(search)}:{restoreSignal}`), losing scroll position and any open control.
- Most settings pages are not code-split beyond the route, and several are very large (`SettingsPanels.tsx` 3,819 lines holds General, Appearance, Archive and About).
- No keybinding command opens Settings or jumps to a page, so the AGENTS "entry points" rule is only met on desktop through the menu accelerator.
- Search does not cover Diagnostics or Open source licenses (they are not `SettingsPath` values), nor the Usage page.

## Remodel goals

- **Experience:** keep the structure the design direction asks for ("Settings is the equipment rack: calm, dense, instant"): nav on the left, page title in `--text-display-s`, sections as raised groups with internal dividers on the stage plane, rows with label, description and control on the right. Device rows and environment rows must be distinguishable at a glance by more than a small per-row marker (the per-row scope wording is decided in E25-T02). Every page reachable from the command palette and by a keybinding, not only the menu.
- **Motion:** section and page switches are cuts (design direction 3.10: settings section switching is instant). Search keeps its one-shot highlight of the target row using the `sweep` preset (reduced: static highlight at 0.3; off: static). Dialogs opened from settings rows use the standard dialog moment (scrim 140 ms, panel 200 ms). No row entry animations.
- **Performance:** the settings route stays inside the 150 KB incremental bundle budget (architecture 3.1) with each page split into its own chunk; scope changes re-render rows instead of remounting the page; the search index is built lazily on first focus of the search box rather than at module load.

- [ ] Search finds every row that exists today (parity test generated from the old catalog), honours every availability flag, ranks keybinding commands last, and lands with the `sweep` highlight; Diagnostics and Licenses become searchable.
- [ ] Esc order (overlay, then field blur, then leave) and the back destination are preserved.
- [ ] Settings, and each page, are reachable from the command palette and from a keybinding (new command ids added to the contract with no default key, or with a default the owner approves).

- [ ] Keyboard: nav, search results and every row control reachable; visible focus; reduced and off motion levels checked.

+++ Agent notes

- Inventory sources: `05:S-1`, `05:S-2`, `05:F-2`, `05:F-37`.
- Rewrite size: L. The shell is small but the search catalog, the availability rules and the shared row primitives touch every settings page.
- **How the search index stays truthful after the rewrite (decide in this task):** today rows opt in by spreading `searchableSetting(id)`, and `settingsSearch.test.ts` checks unique ids and some availability rules. For v2, keep the catalog as the single source for id, title and search terms, but make the row component require a catalog id (a `SettingsRow` without `searchId` fails type-check unless explicitly marked `unsearchable`), and add a test that renders each page's row registry (not markup) and asserts every catalog entry for that page has a matching row and vice versa. Derive availability flags from the same predicate the row uses to decide whether it renders, instead of restating them. Keybinding results stay generated from `STATIC_KEYBINDING_COMMANDS` and `DEFAULT_KEYBINDINGS`.
- Traps: `retainSettingsScope` search middleware keeps the scope when moving between pages but an explicit target replaces the whole selection, and the legacy `environmentId` provider link maps to `machine`; keep both. Search results must never point at an anchor that is not mounted (that is why desktop-only and Windows-only flags exist). The auth gate allows `hosted-static` status through. The nav badges (signed-out providers, saved environments) read live state and must not cause the nav to re-render on every provider status tick.
