# E25-T03 · Client settings persistence and sync

## What it is

The layer that loads, holds and saves **client settings**: the preferences that belong to the device or browser you are using (send shortcut, diff layout, notification mode, fonts, browser preview defaults, confirmations and so on), and the merge of those with the selected environment's **server settings** into one "unified settings" object that screens read. It also covers "Restore device defaults", the one-click reset on the General page, and the small set of server-side preferences that are kept the same on every environment. There is no screen of its own; every settings page and many app surfaces depend on it.

## When it is used

- At startup, before any screen can trust a preference (the sidebar mode, the browser preview's default viewport, the send shortcut).
- Every time a device preference changes, from Settings or from inline controls elsewhere (diff layout toggle, follow-up behaviour).
- When a user changes a preference that is stored on the server but should not differ per machine (for example "Continue threads after restarts").
- When a user wants to undo their customisation with **Restore device defaults**.

## How it works today

- **Entry points:** `useClientSettings`, `useSettings`/`useScopedSettings` hooks, `persistClientSettingsPatch`, `persistClientSettingsUpdate`, `getClientSettings` (non-React), `ensureClientSettingsHydrated`, the General page header button "Restore device defaults".
- **Behaviour to preserve:**
  - **Storage:** web keeps the whole client settings object under localStorage `e6code:client-settings:v1` (`clientPersistenceStorage.ts`); desktop stores it in the main process through the bridge (`desktopBridge.getClientSettings` / `setClientSettings`, `apps/desktop/src/ipc/methods/clientSettings.ts`), so it survives a renderer storage wipe. Values are decoded with `ClientSettingsSchema` (`packages/contracts/src/settings.ts:314`); missing keys take defaults.
  - **Hydration status:** `pending`, `ready`, `failed`, `retrying`. Before `ready` the snapshot is the schema defaults, so code that would bake a value into durable state (opening a browser preview tab with the default viewport, zoom and appearance) must await `ensureClientSettingsHydrated()`. A failed read rejects and stays retryable; defaults must never overwrite saved preferences after a failed read. The legacy-sidebar switch is held at the default until hydration so the app does not mount one sidebar and swap it.
  - **Writes:** persisted before the in-memory snapshot is published; if another write lands while one is pending, the updater is re-applied to the newer snapshot and persisted again so neither change is lost (`persistClientSettingsUpdate`). Persistence errors are logged with a scope tag and surfaced as a toast.
  - **Unified settings:** client and server keys are merged (`mergeEnvironmentSettings`, `UnifiedSettings`); one updater routes each key to the right store (`useUpdateSettingsTarget`). Server keys are patched optimistically in atom state and then sent with `server.updateSettings`. Server writes with no environment toast "Setting not saved" instead of dropping silently. The hosted static web app (`isHostedStaticApp`) may have no primary environment; `usePrimarySettingsAvailable` gates server rows there.
  - **Shared preferences:** six server keys that are user preferences (`continueThreadsAfterServerUpdate`, `sidebarAutoSettleAfterDays`, `sidebarAutoSettleOnMerge`, `newWorktreesStartFromOrigin`, `sourceControlWritingStyle`, `textGenerationModelSelection`) are written to every environment that supports shared-settings sync, filtered per environment by capability (`client-runtime/src/state/sharedSettings.ts`: `splitSharedServerPatch`, `filterSharedServerPatch`, `supportsSharedSettingsSync`). `findSharedSettingsMismatches` can report environments that still hold a different value; the user docs describe an "Apply to all" action for Continue threads after restarts (where the web shows it was not verified; the helper has no web caller).
  - **Restore device defaults** (`useSettingsRestore`, `SettingsPanels.tsx:642`): the button is disabled when nothing differs; a confirmation lists every changed item by name ("This will reset: Theme, Accent, Send shortcut, …"); theme keys (theme, follow system, light/dark mix) are reset first with rollback, and a theme storage failure shows "Couldn't restore theme settings" and stops; then one patch resets the rest; the page remounts. **Despite its name it also resets server settings in the current scope**: response streaming, provider update checks, continue threads after restarts, Jev routing on/off, background activity (profile and intervals), new thread mode, start from origin, add-project base directory, text generation model, auto-settle rules and agent browser access (the dialog names it so the user knows the agent regains access). It also resets "Visible threads" (`sidebarThreadPreviewCount`), which no longer has a row on any page.
- **Surfaces:** web and desktop as above. Mobile shares `ClientSettingsSchema` but persists its own preferences as a sparse JSON patch with a fallback key (`apps/mobile/src/persistence/*`); it is rebuilt in E34. Server: `ServerSettings` also persists a `ClientSettings` schema section (report 06 F-7), not used for web device preferences.
- **Where the code lives:** `apps/web/src/hooks/useSettings.ts` (524), `localApi.ts`, `clientPersistenceStorage.ts`, `hooks/useLocalStorage.ts`, `packages/client-runtime/src/state/sharedSettings.ts` (176), `packages/contracts/src/settings.ts` (1,713), `components/settings/SettingsPanels.tsx:642-990` (restore).

## Problems today

- Client settings are module-level state with hand-rolled listener sets and `useSyncExternalStore`, separate from the Effect atoms used for server state and from zustand used elsewhere (architecture 2.3 asks for one model).
- The whole object is rewritten on every change, in one localStorage blob on web.
- "Restore device defaults" resets server settings across every environment in scope, which its label and placement contradict. Its list of keys is hand-maintained in three places (changed labels, dependency array, reset patch) and already includes a setting with no UI.
- The shared-preference mismatch helper exists but is not wired into the web UI.
- Theme state lives in separate localStorage keys outside this layer (`e6code:theme`, `theme-appearance-mode`, `theme-halves:v1`), so restore has to coordinate two stores with manual rollback.

## Remodel goals

- **Experience:** a preference changes instantly and never "snaps back" after hydration; restore says exactly what it will reset and where (this device vs which environments), and offers separate "Reset this device" and "Reset environment defaults" actions if the owner agrees.
- **Performance:** hydration is on the boot critical path for the shell; it must fit the "interactive from cache ≤ 1.2 s" desktop budget and must not block first themed paint. Writes are per key (or debounced) rather than whole-object rewrites, consistent with the per-key persistence rule in architecture 2.3.

## Done when

- [ ] One client settings store in the chosen v2 state model (E04-T03), shared with mobile through `client-runtime` where possible, decoding the existing persisted data on web (localStorage key) and desktop (bridge) without loss.
- [ ] Hydration status, await-before-durable-use, retry after failure, and no-defaults-over-saved-values are preserved and covered by tests.
- [ ] Concurrent writes cannot lose an update (test).
- [ ] Restore lists changed items, separates device and environment resets (or the owner explicitly keeps today's combined behaviour), and derives its key list from one table.
- [ ] Shared-preference sync behaves as today, and the mismatch warning is either surfaced or the helper removed by decision.
- [ ] Boot timing with hydration measured against the startup budgets.
