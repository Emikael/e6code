# E25-T04 · Server settings service

## What it is

The server service that owns each environment's settings: a `settings.json` file under the environment's state directory, validated against one schema, cached in memory, watched for hand edits, published to every connected client when it changes, and kept free of secrets (API keys and management keys live in the secret store and appear in the file and on the wire only as a redacted marker). Every server behaviour that follows a user choice (cleanup, streaming mode, provider binaries, auto-settle, background intervals, usage price overrides) reads it.

## When it is used

- On server start, before reactors that read policy begin.
- Whenever any client writes a setting (`server.updateSettings`), including fan-out writes from the settings scope (E25-T02).
- When a user or script edits `settings.json` by hand while the server runs.
- Whenever a reactor needs the effective value for a project (project overrides).

## How it works today

- **Entry points:** WebSocket RPC `server.getConfig` / `serverGetConfig`, `server.getSettings`, `server.updateSettings` (a `ServerSettingsPatch`), the `subscribeServerConfig` stream (`settingsUpdated` event), `subscribeChanges` / `streamChanges` inside the server. File: `<state>/settings.json` (normally `~/.e6/userdata/settings.json`).
- **Behaviour to preserve:**
  - **Schema:** `ServerSettings` (`packages/contracts/src/settings.ts:1143`) has about 60 top-level keys: worktree and storage cleanup, response streaming mode (default `paragraph`), provider update checks, continue threads after restart, agent browser and device access, default model, runtime mode and thread environment mode, project scripts and per-project overrides (`ProjectSettingsOverrides`), auto-pull, auto-settle, background activity profile and intervals, published themes and default theme, text-generation model, source-control writing style and merge method, `providers` (legacy per-kind) and `providerInstances` (current map), observability URLs, usage-limit sources and price overrides, device hosts, System One (Jev routing). Keys decode with defaults, so **dropping a key from the schema resets users' values**.
  - **Writes:** validate the patch, apply it, write atomically (`atomicWrite.ts`), update the cache, publish to subscribers. A semaphore serialises writes.
  - **External edits:** a debounced `fs.watch` re-reads the file (events can fire before the write is flushed); invalid content is not applied (exact behaviour on an invalid hand edit: not verified).
  - **Secrets:** provider environment secrets, usage-limit-source management keys and the System One API key are hydrated from the secret store; the JSON keeps `SECRET_VALUE_REDACTED` ("••••••"). A client that sends the marker back means "keep the stored value". Secrets must never be written to `settings.json` or sent to clients.
  - **Project overrides:** 17 keys can be overridden per project entry (list in E25-T02); `packages/shared/src/projectSettings.ts` resolves the effective value for a project and reports the source (environment or project).
  - **Legacy migration:** `providers` (per kind) coexists with `providerInstances`; background activity has a legacy shape resolved by `resolveServerBackgroundActivitySettings`.
  - Related services in the same layer: `Keybindings` (E25-T06), `EnvironmentTheme` (watches `<state>/themes/*.json`, CLI `e6 theme`; owned by E26-T05).
- **Surfaces:** server only; every client reads it through `server.getConfig` and the config stream. Mobile reads and writes the same keys.
- **Where the code lives:** `apps/server/src/serverSettings.ts` (1,144), `packages/contracts/src/settings.ts` (1,713), `apps/server/src/atomicWrite.ts`, `apps/server/src/auth/ServerSecretStore.ts`, `packages/shared/src/projectSettings.ts`, `apps/server/src/environmentTheme.ts` (307), `apps/server/src/keybindings.ts` (685).

## Problems today

- A very large schema with decoding defaults and legacy migration comments: easy to reset a user's value by renaming or removing a key.
- `settingsUpdated` publishes the settings to every subscriber on any change; payload size of the full settings object per change was not measured.
- Settings that are device-like (several `ClientSettings` fields are also in the server schema per report 06) blur the client/server split described in E25-T03.
- These and the git trace file are the only file watchers in the server; behaviour on platforms with unreliable `fs.watch` (network drives, WSL) was not verified.

## Remodel goals

- **Performance:** a settings change reaches other clients as one small event within the WebSocket payload budget (no live frame over 256 KiB, p95 ≤ 4 KiB); measure the size of `settingsUpdated` with a realistic `providerInstances` map and consider sending only changed keys if it is large. Reading settings stays off the hot path of streaming.
- **Experience:** a hand edit to `settings.json` that fails validation is reported to clients (a notice in Settings) rather than silently ignored.

## Done when

- [ ] A schema-evolution rule is written into the contracts package docs and enforced by the contract compatibility test: keys are only added (optional), never renamed or removed without a migration that preserves the user's value.
- [ ] Secrets never appear in `settings.json`, logs or client payloads (test covering each secret-bearing key, including the redacted-marker round trip).
- [ ] Atomic write, serialised updates, debounced external-edit reload and the change stream keep working; invalid hand edits surface as a visible notice.
- [ ] `settingsUpdated` payload size measured and within budget; change-only publishing adopted if it is not.
- [ ] Any client-only keys still mirrored in the server schema are listed with a decision (keep, move, remove).
