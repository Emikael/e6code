# E25-T02 · Settings scope: machine, project, checkout

## What it is

The settings **scope** decides which servers a change is written to and whether it is a machine-wide default or an override for one project. E6 Code can be connected to several **environments** at once (an environment is one running E6 server and the machine it owns: your laptop, a desktop at home, a cloud box). Each environment keeps its own `settings.json`. The scope selector in the settings header lets one page edit all of them together, one of them, one project across them, or one checkout of a project on one machine. Device preferences (theme, fonts, send shortcut) are not affected by the scope at all: they are saved on the device you are using.

In plain terms, the scope has two axes, both kept in the page URL:

- **Machine axis** (`?machine=<environmentId>`): absent means "All environments"; set means one environment.
- **Project axis** (`?project=<projectKey>` and optionally `?checkout=<physicalProjectKey>`): absent means "environment defaults"; a project means "override for this project on every selected machine"; a checkout means "override for this one copy of the project on one machine".

## When it is used

- Changing a default for every machine at once (for example "Continue threads after restarts" on both the laptop and the build box): leave "All environments" selected.
- Giving one project different behaviour (a different default model, auto-pull off, worktree cleanup off for a long-lived repository): pick the project in the breadcrumb.
- Fixing a value that differs between machines: the row shows **Mixed**; pick a value to make them agree, or narrow the scope to one machine.
- Landing from a settings search result that only exists at another scope (the shell then shows a notice with a picker).

## How it works today

- **Entry points:** the breadcrumb (`SettingsScopeBreadcrumb`), deep links carrying `project`, `machine`, `checkout` (and the legacy `environmentId`, mapped to `machine`), settings-search results that carry a required scope, the scope notice picker in the shell, and the Project page's own links.
- **Behaviour to preserve:**
  - **Resolution** (`settingsScope.ts:resolveSettingsScope`): kinds `all`, `environment`, `project`, `checkout`, `unavailable`. Stale ids stay in the URL and resolve to `unavailable` with a message ("This environment is no longer available.", "This project is no longer available.", "This project has no checkout on this environment.", "This checkout is no longer available in the selected project and environment.", "Select a project to choose one of its checkouts.") so a removed target never silently broadens to "all". Projects come from the sidebar's project groups (projects merged across environments by the grouping mode), so the project axis follows `sidebarProjectGroupingMode`; remembered members survive a grouping change.
  - **Labels:** "All environments", environment label, `<Project> / <Environment or "All checkouts">`, and for a checkout `<Project> / <Environment> · <path>` when two checkouts share one environment.
  - **Reads:** one "representative" connected environment (the primary if selected, otherwise the first connected) supplies displayed values; it never decides where writes go (`selectScopedSettingsEnvironments`).
  - **Writes** (`planScopedSettingsPatch`, `persistScopedSettingsPatch`): environment scopes write the patch to every _connected_ environment in scope; project and checkout scopes write only the 17 project-scopable keys into each member's override entry on its own environment (object-valued keys are completed from the target's effective value); client keys always persist locally. All targets are awaited; partial failure raises "Setting saved on some environments — Could not update X. The other selected environments saved the change."; full failure "Setting not saved". A plan that cannot be applied (for example a non-scopable key at project scope) toasts "Setting not saved" with the reason.
  - **Project-scopable keys** (`PROJECT_SCOPED_SERVER_SETTING_KEYS`): `worktreeCleanup`, `defaultModelSelection`, `defaultRuntimeMode`, `defaultThreadEnvMode`, `newWorktreesStartFromOrigin`, `defaultAutoPull`, `defaultProjectScripts`, `enableAgentBrowserAccess`, `enableAgentDeviceAccess`, `textGenerationModelSelection`, `sourceControlWriterModelSelection`, `sourceControlWritingStyle`, `pullRequestMergeMethod`, `sidebarAutoSettleOnMerge`, `sidebarAutoSettleAfterDays`, `continueThreadsAfterServerUpdate`, `responseStreamingMode`. In an override entry an absent key inherits; `null` is a real value where the type is nullable (no default model, never auto-settle).
  - **Mixed and sources:** `scopedSettingsAreMixed` shows "Mixed" when targets disagree; `scopedSettingsSource` reports whether the keys are overridden on every target, inherited on every target, or split. At environment scope a row can list the projects that override it and offer to clear those overrides (`listProjectOverrides`, `useClearProjectOverrides`); at project scope "Reset to inherit" and "Reset all" clear overrides (`useClearScopedSettings`).
  - **Inheritance popover** (`SettingInheritance.tsx`): Project → Environment → Default, each with a formatted value ("Inherits", "On/Off", "Never", "Automatic", "Last selected", writing-style names). For the workspace mode a checkout's `e6.json` preference sits between the environment default and a project override and shows as "Repository default: … (e6.json)".
  - **Capability checks:** rows that need a server capability (project overrides need `projectSettingsOverrides`; auto-settle needs `threadAutoSettlement`) are unavailable or explained when any selected target lacks it.
  - **Shared preferences:** six server keys that are really user preferences (`continueThreadsAfterServerUpdate`, `sidebarAutoSettleAfterDays`, `sidebarAutoSettleOnMerge`, `newWorktreesStartFromOrigin`, `sourceControlWritingStyle`, `textGenerationModelSelection`) are also kept in step across environments by `client-runtime/state/sharedSettings.ts`, which warns when another environment holds a different value and offers "Apply to all" (see E25-T03).
  - Pages that ignore scope: Appearance, SnapShots, Connections (device only, breadcrumb hidden). Providers, Diagnostics and Keybindings read one environment (the representative); Keybindings writes fan out to the selection.
- **Surfaces:** web and desktop as above. Mobile has a simpler model: an environment filter in the settings header plus a project filter, "Use defaults" to clear a page's overrides, project rename under Settings → Projects & threads → Overview (`settings-environment-filter.tsx`, `settings-scoped-server.ts`); it uses the same contract keys. Server: `ProjectSettingsOverrides` in `settings.json`, resolved by `packages/shared/src/projectSettings.ts`.
- **Where the code lives:** `apps/web/src/components/settings/settingsScope.ts` (156), `settingsScopeAxis.ts`, `settingsScopeNavigation.ts`, `scopedSettings.ts` (390), `useScopedSettings.ts` (121), `SettingInheritance.tsx` (301), `SettingsBreadcrumb.tsx` (201), `SettingsScopeContext.tsx`, `SettingsScopeNotice.tsx`, `packages/shared/src/projectSettings.ts`, `packages/contracts/src/settings.ts:1034`; tests next to each (the best specification).

## Problems today

- The concept is powerful but heavy: four scope kinds, two axes, a representative environment, Mixed values and three inheritance layers, explained only through a breadcrumb and a small layers icon.
- Several pages interleave device rows and server rows, and only a per-row marker tells them apart, so a user cannot tell which rows the scope affects.
- Disconnected environments in an "All environments" scope are skipped silently for writes; the user only sees "Mixed" later.
- The entire page remounts on every scope change (`key=` on the serialised search), which is the expensive way to re-read values.
- There is no "checkout" layer in the inheritance chain even though a checkout scope exists; a checkout override is just that member's project entry, which is easy to misread.

## Remodel goals

- **Experience:** a user should always be able to answer "where will this change go?" before changing a value. The scope selector reads as a sentence, every server row says in words what it targets when the scope is broader than one machine, and Mixed values name the machines that differ. Device rows are visually grouped or labelled "This device" so the scope is obviously irrelevant to them.
- **Motion:** changing scope is a cut; only values that changed may cross-fade (`fade`, `dur.state`), and nothing travels. Value chain popovers use `pop` from their trigger.
- **Performance:** scope change re-reads values without remounting the page; fan-out writes are optimistic per row with per-environment confirmation, and never block the control over a remote link (architecture 4.1 rule 6).
