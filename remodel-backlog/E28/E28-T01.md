# E28-T01 · Usage page

## What it is

The Usage page (`/usage`): how much agent work cost and how many tokens it used, across every connected environment, for the last 24 hours, 7, 30 or 90 days. The server scans the provider CLIs' own session transcripts (Codex, Claude Code and Grok Build), so usage includes sessions run outside E6 Code, prices them at API-equivalent rates, and the client merges the per-environment summaries. This is central to the "bring your own subscription" story: users see what their subscription would have cost at API prices and where it went.

## When it is used

- Checking spend or token use this week, and how it compares with the previous period.
- Finding which provider or model consumed the most, and how much caching saved.
- Comparing machines, or excluding one, with the environment filter.
- Seeing Jev routing savings when Jev routing is on.

## How it works today

- **Entry points:** nav rail Usage item (`AppNavRail.tsx`), sidebar chrome, command palette navigation to `/usage`; header breadcrumb "Usage / <environments>"; Settings → Back destination returns to Usage when entered from it. No keybinding. The per-turn "Worked for" summary in the thread (tokens and cost on finished turns, "≈" when estimated) uses the same pricing (owned by the timeline, E13-T09).
- **Behaviour to preserve:**
  - Header: environment filter (breadcrumb menu: "All environments" checkbox, one checkbox per environment with status Ready / Scanning… / Refreshing… / Update required / Unavailable, "No environments connected.", "Totals are partial while selected environments scan.", coverage notices, and **Model prices** which opens E28-T03); metric tabs **Cost / Tokens / Limits**; period **24h / 7 days / 30 days / 90 days**; refresh (rescans session history and updates pricing; on Limits it rechecks limits, E28-T02); date range text.
  - Remembered: metric and period in localStorage `e6code:usage-page-preferences:v1` (first visit: Cost, 7 days). View (chart/table) and environment selection are not remembered.
  - Summary: big total ("Usage · cost, past 7 days"), "N sessions · API price estimate · N environments", period-over-period change chip (computed from a second query for the previous window; hidden while either is partial or empty).
  - Provider share bar and legend (Codex, Claude Code, Grok Build) with amount, share and sessions.
  - Chart: hourly buckets for 24h, daily otherwise, stacked by provider, up to 90 bars, "View as table" / "View as chart"; the table lists periods newest first with a column per active provider.
  - "Where the cost went" or "Where the tokens went" by model, with unknown-cost models flagged.
  - Stat tiles: tokens processed, share of input from cache, output tokens, saved by caching; Jev routing tiles when present (LLM calls avoided, Jev input tokens, Jev cost, Jev calls, average latency).
  - Models table: Model, Cost, Share, Tokens (sorted by tokens on the Tokens tab).
  - Coverage notices: "<env> could not report usage.", "<env> runs an older server version and is excluded from totals." (usage contract version check), "Counted once across environments sharing a transcript directory: …".
  - States: loading skeleton, partial, empty, no environment selected.
- **Server** (`usage/UsageService.ts`): scans transcripts of Claude Code, Codex and Grok Build, caches parse state per file by (size, mtime) with append-resume, prices with a rate table cached for a day (`serverRefreshUsageRates`), aggregates to buckets; RPC `serverGetUsageSummary`. A cold 30-day scan of about 1.4 GB takes 2–3 s in Node.
- **Surfaces:** web and desktop. Mobile: Settings → Usage with Usage/Limits tabs, ranges, Cost/Tokens, native SwiftUI daily chart on iOS, per-provider and SystemOne sections (E34-T07). Cursor, OpenCode and Antigravity sessions are not scanned (not verified whether that is intended; see E37-T11).
- **Where the code lives:** `apps/web/src/components/usage/UsagePage.tsx` (1,229), `UsageProviderChart.tsx` (357), `usageInsights.ts`, `usagePagePreferences.ts`, `usageProviders.ts`, `packages/shared/src/usageMerge`, `usageShares`, `usageFormat`, `packages/client-runtime/src/state/usage.ts`; server `apps/server/src/usage/UsageService.ts` (838), `usageTranscripts.ts`, `usageTranscriptReader.ts`, `usageScanCache.ts`, `usagePricing.ts`, `usageAggregation.ts`.

## Problems today

- One 1,229-line component holds metric, window, filter, view, refresh and limits clock state.
- A second full summary query per window change exists only for the delta chip.
- Custom DOM chart (no chart library) re-rendered as DOM with up to 90 bars; provider colours are hard-coded hex (Claude `#d97757`) against the semantic colour rule.
- Monospace is used for summary lines and numbers beyond what the type rules allow.
- The scan runs on the server's main loop; the architecture plan names it as a candidate for a worker or the `e6-scan` Rust helper if it stalls streaming.

## Remodel goals

- **Experience:** answer three questions at a glance (how much, compared with when, where it went), with values readable without hover, and coverage problems stated next to the total, not hidden in a menu.
- **Motion:** totals roll once with `numberChange`; `RevealText` is not used; charts have no animated loops (design direction "Settings and usage"); switching tabs or periods is a cut with data cross-fade at most.
- **Data display:** one hue family per series role through semantic tokens (no hex), tabular numbers in sans, mono only for ids; table view as the accessible equivalent of every chart.
- **Performance:** derive the previous-period delta from one query that returns both windows (or from cached buckets); the chart renders as one SVG or canvas path; the page fits the 150 KB incremental route budget; server scans keep event-loop delay ≤ 20 ms p99.
