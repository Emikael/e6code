# E35-T04 · Mobile observability and diagnostics

## What it is

The mobile app's observability: how the maintainer finds out what went wrong on a user's phone. Today it has three pieces. **Relay-client tracing**: OpenTelemetry traces for the app's calls to the E6 Connect relay, exported to Axiom when the build has public tracing config. **Trace ids in errors**: connection and relay errors show a trace id with "Copy trace ID", so a user can hand the maintainer an id that matches a server or relay trace. **Startup crash log**: fatal JavaScript errors during launch are recovered from the `expo-updates` log and listed in Settings > Diagnostics (E34-T08). Development-only debug logs exist for cloud and terminal code.

## When it is used

- A user reports "pairing fails" or "the relay keeps disconnecting": the trace id they copy leads to the matching spans.
- The app crashes on launch after an update: the startup crash report is the only record, because TestFlight and the stores strip these.
- The maintainer debugging relay latency, DPoP clock-skew failures or device registration.

## How it works today

- **Entry points:** none for users except "Copy trace ID" on error rows (environments, E6 Connect page, alerts) and Settings > Diagnostics. Developers enable cloud debug logs with `__DEV__` or a global flag (`__E6_CLOUD_DEBUG__`).
- **Behaviour to preserve:**
  - Tracing layer from `@e6tools/shared/relayTracing` (`makeRelayClientTracingLayer`) with service name `e6-mobile-relay-client`, runtime `react-native`, client `mobile-<variant>`, and the app version; disabled (no exporter) when the build lacks `observability` public config (traces URL, dataset, token, read from the repo-root `.env` at build time).
  - Spans go to the shared relay dataset in Axiom (`e6-code-relay-traces-<stage>`) through a mobile-specific, write-only ingest token; relay DPoP failures carry `relay.dpop.failure_code` and the client uses it to tell confirmed clock skew from other causes.
  - Trace ids from connection errors are stored with the environment's connection state and shown next to the error (`ConnectionTraceId.tsx`), with a copy haptic.
  - Startup crash parsing from `Updates.readLogEntriesAsync` over 7 days, keeping only ErrorRecovery fatal exceptions, with a copyable report including app identity.
  - Debug logs are silent in production.
- **Surfaces:** server observability (logs, local trace files, OTLP, browser trace forwarding; E38-T05) and desktop observability (E30-T11) are separate; web forwards browser traces through the server's `/api/observability/v1/traces` proxy. The relay's Axiom setup is in `docs/operations/relay-observability.md`. Mobile does not export traces for its direct environment RPC traffic, only for relay clients (not verified whether environment RPC spans exist locally).
- **Platform differences:** none in the JavaScript layer; the same tracing layer and crash parser run on iOS and Android. Native crashes (Swift, Kotlin, C++ in the native modules) are not captured by the app on either platform.
- **Where the code lives:** `apps/mobile/src/features/observability/tracing.ts` (41) and its test, `packages/shared/src/relayTracing.ts`, `apps/mobile/src/features/cloud/publicConfig.ts`, `features/connection/ConnectionTraceId.tsx`, `features/diagnostics/crash-log-model.ts`, `features/cloud/cloudDebugLog.ts`, `features/terminal/terminalDebugLog.ts`, `scripts/lib/public-config.ts`.

## Problems today

- Only relay calls are traced; the rest of the app (screen loads, RPC latency to environments, render stalls) has no telemetry, so the performance budgets cannot be measured on real devices.
- No capture of crashes after startup or of native crashes, which matter given seven native modules.
- Builds without public config have no tracing at all, which is right for privacy but means contributor builds report nothing.

## Remodel goals

- **Performance:** mobile needs measurement for the M7 budgets: cold start to cached shell, thread open, diff open, terminal reattach. Add local performance marks that the screenshot/showcase harness and developers can read, consistent with the web harness (E05-T02), before adding any remote export.
- **Experience:** errors a user can act on always carry a copyable trace id; a "Share diagnostics" action bundles version, recent crash records and trace ids.
- Respect privacy: anonymous by default, no account emails or file contents in spans, and the same opt-out rules as product telemetry (`docs/user/telemetry.md`).

## Done when

- [ ] Relay-client tracing, trace-id copy and startup crash capture preserved.
- [ ] Decision recorded on native and post-startup crash capture (for example the platform crash reporters or a self-hosted collector) and on tracing environment RPC.
- [ ] Local performance marks for the M7 budgets exist and are documented for the harness.
- [ ] No personal data in spans (checked against a list of attributes).
- [ ] Tracing remains fully disabled in builds without public config.
