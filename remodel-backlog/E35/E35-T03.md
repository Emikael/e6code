# E35-T03 · Share extension and incoming shares

## What it is

E6 Code appears in the system share sheet on iOS and Android. A user can share text, a web link, or images, videos and files from any app (Photos, Safari, Files, a crash screenshot) into E6 Code, which opens the new task flow with the shared content already in the draft. Shares are first saved to a durable _share inbox_ on the phone's filesystem, so nothing is lost if the app is killed before the user finishes, and each share is consumed only once the task is actually created.

## When it is used

- Sending a screenshot of a bug to an agent: "fix this layout".
- Sharing a URL (an issue, a doc page) as the starting point of a task.
- Sharing log files or a short video recording of a problem.

## Current screen

No screenshot: mobile screens could not be captured in this environment (no simulator). Capture with `pnpm screenshots:mobile` on a Mac; see `docs/operations/mobile-app-store-screenshots.md`. (The share sheet itself is system UI; capture by hand on a device.)

Layout in words: E6 Code appears as a target in the system share sheet under its display name (set per variant by a config plugin). After choosing it, the app opens the new task flow's **Choose project** sheet with a subtitle about the incoming share (E34-T01); after a project is picked, the Draft shows the shared text in the editor and the shared media and files in the attachment strip, with any warnings shown (for example "Only the first 8 shared images were attached.", "'name' was skipped because this server does not support files.", "One shared item was not a supported image.", size-limit messages, "'name' is empty or could not be read.").

## How it works today

- **Entry points:** iOS share extension (`<bundle id>.sharing`) and Android share intents (single and multiple, any MIME type); the app receives the payload through `expo-sharing` and routes to `new` with `incomingShareId`.
- **Behaviour to preserve:**
  - Accepted content on iOS: text, at most 1 web URL, up to 8 images, 8 movies, 8 files (activation rule in `app.config.ts`). Android accepts any MIME type, single or multiple.
  - Payloads are converted into a share draft and written atomically to the inbox before the native payload is cleared; replayed payloads are deduplicated by a content-derived id and cleaned up (`incoming-share-inbox.ts`).
  - Lifecycle: a share is **reserved** for a destination project when the user picks one, **released** if they back out or choose another project, and **consumed** only after the task is created; failures roll back (`IncomingShareProvider.tsx`).
  - Attachment limits come from the contracts (`PROVIDER_SEND_TURN_MAX_ATTACHMENTS`, max file and image bytes); oversized, empty, unreadable or unsupported items are skipped with a specific warning; servers without file support skip files with a warning.
  - Shared content merges with an existing draft rather than replacing it.
  - The URL-scheme wakeups that `expo-sharing` triggers are ignored by the app's deep-link filter (`shouldHandleAppLink`, E31-T08).
  - Disabled on iOS Personal Team builds (they cannot sign app groups or extension targets).
- **Surfaces:** mobile only. Web and desktop accept the same kinds of content by drag-and-drop and paste into the composer (E14-T03) and by dropping files onto a sidebar thread row (E09-T04); there is no OS share target for desktop.
- **Platform differences:** iOS uses a separate share extension target with an app group (`group.<bundle id>`) to hand data to the app; Android uses share intent filters on the main activity. The display name plugin (`plugins/withShareExtensionDisplayName.cjs`) applies only where the extension exists.
- **Where the code lives:** `apps/mobile/src/features/sharing/incoming-share-model.ts` (448), `IncomingShareProvider.tsx` (356), `incoming-share-inbox.ts` (201), `incoming-share-storage.ts`, `incoming-share-presentation.ts`, `incoming-share-native.ts`, `apps/mobile/app.config.ts` (`sharingPlugin`), `apps/mobile/plugins/withShareExtensionDisplayName.cjs`.

## Problems today

- The user cannot target a specific existing thread from the share sheet; every share starts a new task.
- Warnings appear only after a project is chosen, so the user learns late that items were skipped (not verified whether warnings show earlier).
- The share extension has no UI of its own; the transition from the share sheet to the app is abrupt.

## Remodel goals

- **Experience:** sharing should feel like "hand this to an agent": the app opens straight to the project choice with a compact preview of what is coming (thumbnails, file names, skipped items with reasons). Consider letting the user add the share to an existing thread as well as a new one.
- **Motion:** the shared items land in the draft's attachment strip in place, without a stagger; under reduced motion they simply appear.
- **Performance:** building the share draft (reading and copying files) must not block the first frame of the new task sheet; show the sheet first and fill attachments as they are ready.
