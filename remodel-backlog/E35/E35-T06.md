# E35-T06 · Native dev workflow tooling

## What it is

The developer tooling that keeps the mobile app's native side workable for a solo maintainer and for agents: a script that decides whether the installed development client is still compatible with the current native code and rebuilds it only when needed, static analysis for Swift and Kotlin, and the Fast Refresh plumbing that lets JavaScript edits apply without restarting the app. It is not user-facing, but every mobile task in the remodel runs through it.

## When it is used

- Before starting Metro for mobile verification: `node scripts/mobile-native-client.ts ensure <ios|android> <device-id>` checks the Expo fingerprint of native inputs and builds and installs a new client only if it is missing or stale (AGENTS.md treats a missing or outdated client as a build step, not a blocker).
- In CI: the "Mobile Native Changes" and "Mobile Native Static Analysis" jobs (SwiftLint, ktlint, detekt) run when Swift, Kotlin or their configs change.
- During daily work: editing a connection-runtime module or a style should refresh in place without losing state.

## How it works today

- **Entry points:** `scripts/mobile-native-client.ts check|ensure <platform> <device>`, `scripts/mobile-native-static-check.ts`, `apps/mobile` scripts (`dev:client`, `ios[:dev|:preview|:prod]`, `android[...]`, `generate`, `sync:pierre-icons`, `profile:android:hermes`), `apps/mobile/Brewfile`, `.swiftlint.yml`, `detekt.yml`, CI jobs in `.github/workflows/ci.yml`.
- **Behaviour to preserve:**
  - Fingerprint check: the Expo fingerprint for the platform is compared with the recorded fingerprint of the installed binary; statuses `compatible`, `missing`, `unknown`, `stale`. `ensure` rebuilds and records only if native inputs did not change during the build ("Native inputs changed during verification. Run ensure again"). iOS checks must run on the Mac hosting the simulator.
  - Static analysis tools are discovered with install hints; source discovery errors are typed.
  - Fast Refresh: the connection runtime sits behind a hot-swappable atom runtime that installs the new Effect layer before accepting an update; the shared atom registry is never reset; production uses an ordinary runtime (`docs/internals/mobile-development.md`).
  - The Uniwind patch still compiles CSS on Metro updates but skips global style invalidation when the generated stylesheet and theme list are unchanged.
  - Local Expo modules under `apps/mobile/modules/` are `file:` dependencies copied by pnpm; TypeScript edits to a module are invisible to a running client until `vp i` re-syncs them, while Gradle and CocoaPods compile the worktree directly.
  - Theme generation (`generate-uniwind-themes.mts`) writes mobile theme files and widget status colours from `@e6tools/shared/themePalettes`.
  - Runtime version policy: fingerprint for release variants, app version for development, so dev builds do not churn.
- **Surfaces:** mobile and platform tooling. Related: the native helper build pipeline and native modules overview (E39-T03), the store screenshot harness (E35-T05), OTA updates (E31-T10).
- **Platform differences:** iOS builds need Xcode and CocoaPods on macOS (including a CocoaPods UUID cache plugin and Personal Team capability stripping); Android builds need the JDK and Gradle (a heap-size plugin; JDK 21 for Robolectric API 36 tests). The `react-native-screens` patch adds native header props that require code generation and a new binary.
- **Where the code lives:** `scripts/mobile-native-client.ts`, `scripts/mobile-native-static-check.ts` (+ test), `apps/mobile/src/lib/hot-swappable-atom-runtime.ts`, `foundation-fast-refresh.ts`, `uniwind-dev-refresh`, `patches/uniwind@1.11.0.patch`, `patches/react-native-screens@4.26.2.patch`, `apps/mobile/scripts/generate-uniwind-themes.mts`, `apps/mobile/plugins/*`, `apps/mobile/.swiftlint.yml`, `apps/mobile/detekt.yml`, `apps/mobile/Brewfile`, `apps/mobile/eas.json`, `apps/mobile/README.md`, `docs/internals/mobile-development.md`.

## Problems today

- The module copy behaviour (`file:` dependencies) makes "my change has no effect" a recurring trap.
- The design-token pipeline planned for M0 (architecture 2.6) will replace the theme generator's input; the generator and widget colour injection must move with it.
- Native toolchains are heavy; agents without a Mac cannot verify iOS.

## Remodel goals

- **Performance:** keep rebuilds rare (fingerprint gate) and Fast Refresh reliable, so the many mobile screen tasks iterate quickly.
- Move theme generation onto the shared design-tokens package so mobile, widgets and web read one source.
- Make module edits visible without a manual `vp i`, or fail loudly when the copy is stale.

## Done when

- [ ] `check` and `ensure` behave as above on both platforms and are documented for agents.
- [ ] Theme and widget colour generation reads the design-token package (E01) with unchanged output for the stock palette.
- [ ] A stale local-module copy is detected (warning or automatic sync).
- [ ] CI native jobs still trigger on the same paths and pass.
- [ ] Fast Refresh behaviour preserved, with the runtime boundary rules kept.
