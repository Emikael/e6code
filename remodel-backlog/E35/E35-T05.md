# E35-T05 · Showcase mode and store screenshots

## What it is

The tooling that produces App Store and Google Play screenshots of the real mobile app. `pnpm screenshots:mobile` starts three disposable local E6 servers with deterministic Git projects and seeded threads, builds and boots iOS simulators and Android emulators, pairs a clean app installation with every server through the normal pairing flow, navigates to five real routes (Home thread list, Thread, Terminal, Review, Settings > Environments), and writes store-ready PNGs. A build flag, `EXPO_PUBLIC_SHOWCASE=1`, turns on a non-rendering coordinator in the app that handles pairing, readiness signals, palette and orientation for the harness. It is not user-facing. The user-facing side is the store listing: people install the app from the App Store or Google Play and then pair it with a server.

## When it is used

- Before a store release, to refresh listing screenshots in dark, light and every built-in palette.
- After a visual change, to check the five key screens on six device sizes in one run.
- During the remodel: it is the only automated way to capture mobile screens, so every redesigned mobile screen task depends on it for before/after evidence.

## How it works today

- **Entry points:** `pnpm screenshots:mobile` (repo root, runs `scripts/mobile-showcase.ts`); `vp run screenshots` and `vp run showcase` in `apps/mobile`; options `--appearance light|dark|both`, `--theme <id>|all`, `--skip-build`, `--keep-running`.
- **Behaviour to preserve:**
  - Real app, real routes: no screenshot-only screen recreates UI. Showcase mode only enables the pairing/readiness coordinator, disables terminal autofocus so captures have no keyboard, and supplies deterministic E6 Connect discovery rows to the real Environments screen (`showcaseEnvironmentRows.ts`); local environment cards always come from real paired servers.
  - Seeded data: three servers ("Moonbase Terminal", "Suspense Station", "Kernel Cabin"), E6 Code, React and Linux repositories with favicons, feature branches and a deterministic review diff, seeded threads, messages, activities and terminal history, and two outbox tasks waiting to send (`showcasePendingTasks.ts`).
  - Readiness: each scene waits for the environment snapshot to hydrate and the route to become active, and reports ready only once the requested palette is applied; readiness is recorded in the app container on both platforms (`ShowcaseCaptureCoordinator.tsx`, `showcaseRenderSignal.ts`, native hooks in `e6-native-controls`).
  - Output matrix: iPhone 6.9" and 6.5", iPad 13" landscape, Google Play phone, 7" and 10" tablets; 30 dark PNGs by default, 60 with both appearances, times six with all palettes (`e6-code`, `e6-chat`, `grove`, `ocean`, `ember`, `iris`); RGB PNGs without alpha, validated for size, aspect and count, written under `artifacts/app-store/screenshots/`.
  - Clean production prebuild before a full capture; all servers, Metro, devices and temp directories are cleaned up unless `--keep-running`.
  - Fixed Metro port 8199 shared across checkouts.
- **Surfaces:** mobile and platform tooling (Node scripts outside `apps/mobile`). Web has its own screenshot pipeline for the remodel (E06-T04). Store install steps for users are in `docs/user/install.md` (E40-T04 covers distribution).
- **Platform differences:** iOS captures need a Mac with Xcode simulators (iPhone 17 Pro Max, a disposable iPhone 14 Plus, iPad Pro 13"); Android captures use Pixel AVDs at fixed densities. Status bars are normalised per platform. Readiness and theme hooks are implemented in both the Swift and Kotlin sides of `e6-native-controls`.
- **Where the code lives:** `scripts/mobile-showcase.ts`, `scripts/mobile-showcase.config.ts`, `scripts/mobile-showcase-environment.ts`, `scripts/mobile-showcase.test.ts`, `apps/mobile/src/features/showcase/*` (`ShowcaseCaptureCoordinator.tsx` 312, `nativeShowcaseScene.ts`, `showcaseRetry.ts`, `showcaseRenderSignal.ts`, `showcaseEnvironmentRows.ts`, `showcasePendingTasks.ts`), `apps/mobile/modules/e6-native-controls` (showcase hooks), `docs/operations/mobile-app-store-screenshots.md`.

## Problems today

- Only five scenes exist; most mobile screens (settings, new task, git, files, notifications, widgets) cannot be captured automatically, which leaves 50+ mobile screen tasks without screenshots.
- Concurrent harnesses in different worktrees collide on Metro port 8199 (the readiness check only verifies the port is open).
- Requires a Mac for iOS; this planning environment could not capture anything.

## Remodel goals

- Extend the harness into the remodel's mobile evidence tool: add scenes for each rebuilt screen (still real routes, still seeded data) so every M7 task can attach before/after captures in dark and light.
- Add per-scene performance marks (open time, first content) so the mobile budgets have numbers from the same runs (with E35-T04).
- Keep the store output exactly as today.

## Done when

- [ ] `pnpm screenshots:mobile` still produces the store matrix with the same validation.
- [ ] Scenes added for the rebuilt mobile screens, each waiting on real readiness, never on sleeps.
- [ ] Metro port chosen per worktree or ownership verified, so concurrent runs cannot attach to the wrong Metro.
- [ ] Seeded data shared with the web screenshot pipeline (E06-T04) where possible.
- [ ] Harness tests kept (`mobile-showcase.test.ts`, showcase unit tests).
