# E35-T01 · Agent awareness: push, Live Activities, ongoing notifications

## What it is

_Agent awareness_ tells the user what their agents are doing when the app is closed. It has three parts: **Device Notifications** (push alerts when an agent finishes, fails, needs approval or asks a question; tapping one opens the thread), **Live Activity Updates** on iOS (an "Agent Activity" card on the lock screen and in the Dynamic Island that follows running work), and **Ongoing Agent Activity** on Android (an ongoing notification card that Android 16+ can promote to a Live Update status-bar chip reading "Working", "Approve" or "Answer"). Delivery goes through E6 Connect: each environment publishes agent activity snapshots to the relay, and the relay sends APNs or FCM pushes to the user's registered devices. A direct LAN or Tailscale connection alone does not deliver push.

## When it is used

- The user starts a long task, locks the phone, and wants to know when it needs them or is done.
- An approval is waiting: the alert (or the "Approve" chip) brings the user straight to the decision.
- Several agents run across machines: one card summarises them ("2 agents need attention", up to five threads with project and status).
- Finished results stay on the lock screen for up to 15 minutes, so the user can glance at the outcome.

## How it works today

- **Entry points:** Settings > Notifications; a notification tap (deep link to the thread, or the aggregate's priority thread); Live Activity tap; Android Live Update chip; the app arms a Live Activity locally when the user starts work in the foreground (new task send, E34-T01).
- **Behaviour to preserve:**
  - Requires E6 Connect sign-in (E34-T04) and environments with agent activity publishing enabled (server `AgentAwarenessRelay`, `publish_only` or managed link; `e6 connect publish`).
  - Device registration with the relay per signed-in user: native push token (APNs or FCM), a stable device id, preferences, and on iOS per-activity Live Activity push tokens; retried every 15 s on failure; cleared on sign-out, account change and disable (`remoteRegistration.ts`, a 1,180-line state machine of named operations such as `read-native-push-token`, `prime-live-activity`).
  - APNs environment (sandbox or production) resolved per app variant.
  - Agent states: starting, running, waiting for approval, waiting for input, completed, failed, stale. Quiet running work lives two hours on the relay; approval/input states 24 hours; finished cards expire 15 minutes after the newest result, and replays never extend that deadline.
  - Foreground quiet: ordinary alerts are silent while the app is in the foreground on that phone; ongoing activity keeps updating; viewing a thread on another device does not silence the phone. A foreground-suppressed alert is never shown later.
  - Grouping: simultaneous attention or completion transitions produce one grouped alert; the same states published again never alert twice; completions older than two minutes never alert.
  - Cold start or a foreground after at least 60 s replays the aggregate silently; an empty replay removes an orphaned card; dismissal survives restart.
  - Android: requires Android 7.0+ (API 24) and Google Play services; channels from API 26; permission prompt from API 33; Live Update promotion on API 36 subject to system settings; API 24–25 expire cards with one inexact alarm. Force-stopping the app blocks push until reopened. Dismissing a card does not disable alerts.
  - If the installed native module lacks required methods, Settings disables notifications with "Install a newer app build to enable notifications".
  - Tap handling consumes the last notification response once on cold start and ignores duplicates (`notificationNavigation.ts`).
- **Surfaces:** mobile is the receiver. Server: `AgentAwarenessRelay` publisher (`07:F-13`) and `/api/connect/preferences`. Relay: `infra/relay/src/agentActivity/*` (APNs, FCM HTTP v1, devices, Live Activities, delivery queues; `07:F-12`). Web and desktop have in-app toasts and desktop OS notifications for the same events (E12-T04), not push; Settings > Connections > "Publish agent activity" turns publishing on (E29-T07). The relay contracts are in `packages/contracts/src/relay.ts`.
- **Platform differences:** implemented twice. iOS: `expo-notifications` for alerts plus the "Agent Activity" Live Activity in SwiftUI via `expo-widgets` (`src/widgets/AgentActivity.tsx`, `agentLiveActivity.ios.ts`), push-updated through APNs Live Activity tokens. Android: a native Kotlin module `modules/e6-agent-notifications` (`AgentNotifications.kt`, `AgentActivityPresentation.kt`) that receives FCM data messages, renders the ongoing card and Live Update promotion, with Robolectric tests across API 24, 25, 26, 33 and 36.
- **Where the code lives:** `apps/mobile/src/features/agent-awareness/*` (`remoteRegistration.ts` 1,180, `liveActivityPreferences.ts`, `notificationPermissions.ts`, `notificationPayload.ts`, `notificationNavigation.ts`, `notificationResponseConsumer.ts`, `androidNotifications.ts`, `registrationPayload.ts`, `capabilities.ts`), `src/widgets/AgentActivity.tsx` (411), `apps/mobile/modules/e6-agent-notifications/*`, `features/settings/SettingsNotificationsRouteScreen.tsx` (499); server `apps/server/src/relay/AgentAwarenessRelay.ts` (641); relay `infra/relay/src/agentActivity/*`; docs `docs/user/mobile-notifications.md`, `docs/operations/android-notifications.md`.

## Problems today

- The registration state machine is 1,180 lines and the hardest mobile code to change safely.
- iOS and Android implementations diverge in structure (JS-driven Live Activity vs native Kotlin receiver), so a change to states or wording must be made twice, plus in the relay.
- Status colours are generated into the widget from the stock palette only; a user's theme does not reach the lock screen.
- Testing needs real devices, Firebase and relay configuration; the smoke script verifies only Firebase-to-device delivery.

## Remodel goals

- **Experience:** the lock screen speaks the same status vocabulary as the app (icon + word for Working, Needs approval, Needs your answer, Done, Failed, from the shared view model). Haptics are mobile's key light: an approval arriving is a warning, a turn landing is a success, streaming is silent. Settings explains in one line what each toggle does and what it needs (E6 Connect, publishing).
- **Motion:** none in Live Activities beyond what the OS animates; the in-app response to a tapped notification is a direct cut to the thread with the decision surface in view.
- **Performance:** registration work must not delay launch; it runs after first render and retries in the background.
