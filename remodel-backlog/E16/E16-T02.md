# E16-T02 · Pending approval and hold-to-allow

## What it is

When the permission mode does not let the agent act on its own, the provider pauses and asks: run this command, change these files, read this file, grant this permission, or let an app access something. The user approves once, approves for the rest of the session, always allows, declines, or declines with instructions ("Decline and tell Claude: use the existing script instead"). Commands that are hard to undo (destructive commands such as `rm -rf` or a force push) cannot be approved with a click: the user must **hold** the Approve button for one second, and they can never be allowed for the whole session.

## When it is used

- Supervised or Auto-accept-edits threads, every time the agent wants to run a command.
- Any thread when the agent tries something destructive.
- Codex asking for app access (MCP elicitation); OpenCode asking to read `.env` files; Antigravity asking even in Full access.

## How it works today

- **Entry points:** composer approval panel buttons and overflow menu ("More approval options"); the frontier card (E16-T01); Enter in the composer while instructions are typed sends "Decline and tell"; a held Cmd/Ctrl+Enter for hold-to-allow; Enter/Space held on the focused hold button; pointer press-and-hold.
- **Behaviour to preserve:**
  - Request kinds and labels: "Command approval", "File change approval", "File read approval", "App permission approval", "App access approval" (MCP elicitation, shown as prose rather than mono). The detail is scrollable and focusable (max height, full command). The subagent that asked is named. Several pending requests show "1/N".
  - Decisions: `accept` (Approve), `acceptForSession` ("Always allow this session"), `acceptAlways`, `decline` (Decline), `cancel` (Cancel). The option set comes from the provider: Grok's "Always allow this session" remembers the matching command or tool input; OpenCode offers "Allow once" and "Allow for workspace"; Codex app access offers one request, session, or permanent. Native option IDs must survive (a label is not a valid reply).
  - "Decline and tell <agent>": appears beside plain Decline once instructions are typed in the composer (up to 8,000 characters, `PROVIDER_APPROVAL_FEEDBACK_MAX_CHARS`); plain Decline never clears the typed text. Claude and OpenCode receive the reason natively with the rejection; Codex, Cursor, Grok and Antigravity receive it as the next user message (`supportsApprovalFeedback` is true for all, so the UI cannot tell today).
  - **Hold-to-allow:** destructive commands are detected by `@e6tools/client-runtime/destructiveCommands` with a reason shown above the command. Approve becomes a hold of `HOLD_TO_CONFIRM_MS` (1,000 ms) by pointer (with pointer capture; release, cancel or lost capture aborts), Enter/Space on the button (Space on keyup must not click), or a held Cmd/Ctrl+Enter. Session and always-allow options are removed for destructive commands. A click with no hold (Voice Control, switch access, screen-reader activate) opens a confirmation dialog naming the reason. A live region announces progress; the fill is a CSS `scaleX` transform, hidden under reduced motion.
  - **Held-shortcut detection:** macOS and Electron may never send keyup for Enter while Cmd is held, so a Cmd+Enter hold is trusted only while the key keeps auto-repeating: the first repeat must arrive within 600 ms (`SHORTCUT_FIRST_REPEAT_GRACE_MS`, the OS repeat delay), later ones within 150 ms (`SHORTCUT_REPEAT_WATCHDOG_MS`), otherwise the hold lapses. Any keyup of Enter, Meta or Control, or any key released while Cmd/Ctrl is down, ends it; a fresh keydown means Enter was released. The shortcut applies only with focus inside an element marked `data-approval-shortcut-scope` (composer and approval cards), never with nothing focused, and stands down if another handler already claimed the key. While a hold button is on screen (`data-destructive-approval-hold`), the pull-request merge shortcut (also Mod+Enter) stands down so one press can never do both.
  - Buttons disable while the response is in flight; answered approvals appear as rows in the work log (approval-feedback rows).
  - **Per provider (E37-T11):** all six raise approvals; Antigravity can ask even in Full access; OpenCode follows permission modes with Auto equal to Supervised.
- **Surfaces:** web and desktop. Mobile: `PendingApprovalCard` with its own `HoldToAllowButton` and subagent attribution (E32-T06), sharing `approvalFeedback` and `destructiveCommands` from client-runtime. Server: `request.opened` activities, `thread.approval.respond` (exact command name not verified), adapters map decisions.
- **Where the code lives:** `apps/web/src/components/chat/ComposerPendingApprovalPanel.tsx` (93), `ComposerPendingApprovalActions.tsx` (173), `HoldToAllowButton.tsx` (205), `holdToConfirm.ts` (149), `ChatView.tsx:9166` (`onRespondToApproval`), `ChatComposer.tsx` (approval-state key handling, `submitApprovalFeedback`), `packages/client-runtime/src/destructiveCommands.ts`, `approvalFeedback.ts`.

## Problems today

- The hold shortcut relies on key auto-repeat timing, which differs by OS and user repeat settings; a user with key repeat disabled cannot use the keyboard hold (pointer and Enter/Space still work).
- Actions differ between the frontier card and the composer panel (overflow only in the composer).
- Users cannot see whether "Decline and tell" reaches the agent natively or as a new message.

## Remodel goals

- **Experience:** the approval is the content of the single decision surface (E16-T01): one sentence of what, the exact command or path in mono expandable to full, Approve primary and focused, Decline, "Decline and tell <agent>" as a secondary text action, always-allow options behind a small menu. Destructive commands show the reason in words with an icon and the hold affordance ("Hold to allow").
- **Motion:** the hold fill uses `ease.linear` and tracks the hold exactly (design direction §3.4 step 5); release before completion snaps back instantly. Resolution collapses into a log row with `checkDraw`.
- **Performance:** responding is optimistic (button state changes at once); the server acknowledgement never gates the UI change, but a failure restores the request.
