# E16-T01 · Decision surface (replaces the frontier card)

## What it is

When the agent needs the user, something has to say so at the place the user is looking. Today that is the **frontier card**: a strip at the end of the timeline (the "frontier", where the current turn ends) that appears whenever an approval, a question or a ready plan is waiting, with the matching quick actions. The same request also shows in the composer's panel and in the scroll-to-end pill. This task replaces those three copies with the design direction's single **decision surface**: one canonical place, at the frontier and attached to the composer, that always shows what the user must do next. It owns the "an approval arrives" signature moment. The content of each decision (approval detail, question form, plan actions) is owned by E16-T02, E16-T03 and E16-T04.

## When it is used

- An agent asks to run a command, change a file, read a file, or access an app (approval).
- An agent asks one or more questions (question).
- A plan-mode turn finishes with a proposed plan (plan ready).
- A turn fails and the error belongs at the end of the conversation.

## How it works today

- **Entry points:** appears automatically; actions on the card; the scroll-to-end pill ("Approval waiting · Scroll to turn", "Question waiting · Scroll to turn") jumps back to it; sidebar row status ("Needs approval", "Needs your answer") and header pill lead to the thread; OS notifications for unfocused windows (E12-T04).
- **Behaviour to preserve:**
  - The frontier renders at the end of the timeline only when the timeline has rows and is not a paint-only held timeline (during thread switch); it stacks an inline thread error above the decision (`FrontierStack`). Before the timeline has rows, a thread error stays in the top overlay so a failed first send is never invisible; when the user is scrolled away, the error shows in the overlay as well.
  - Precedence: approval, then question, then plan ready.
  - Approval: label names the subagent when one asked ("<subagent> wants to run a command", via `SUBAGENT_APPROVAL_PHRASE`), else "Approval required at turn frontier"; shows the command or detail in mono; actions Decline, "Decline and tell <agent>" (focuses the composer where the instructions are typed, so card and composer never hold two drafts), Approve, or a hold-to-allow button for destructive commands (its keyboard shortcut is owned by the composer's copy, `shortcutEnabled={false}` here). A new request remounts the hold button so a confirm dialog never approves a different request.
  - Question: "<subagent> needs your answer" or "Agent waiting for your response", action "Answer below".
  - Plan ready: "Plan ready to implement", actions "In new thread" and "Implement plan" (disabled while a send is busy).
  - Buttons disable while a response for that request is in flight (`respondingRequestIds`).
  - The card carries `data-approval-shortcut-scope` so the approval shortcut works there.
  - Pending approvals and questions also hold the message queue (E15-T05).
  - Status elsewhere: header pill and sidebar status words with icons ("Needs approval", "Needs your answer"); warning and info dots are always paired with words.
- **Surfaces:** web and desktop. Mobile shows in-timeline cards (`PendingApprovalCard`, `PendingUserInputCard`) next to the composer and a warning haptic (E32-T06). Server: pending requests are derived from `request.opened` / `user-input.requested` activities (`@e6tools/client-runtime/pendingRequests`).
- **Where the code lives:** `apps/web/src/components/ChatView.tsx:590` (`FrontierStack`), `:3880-3900` (error placement), `:10544-10740` (card and scroll pill, inline JSX), `chat/HoldToAllowButton.tsx`, `packages/client-runtime/src/pendingRequests.ts`.

## Problems today

- The same pending approval appears in three places (frontier card, composer panel, scroll pill), which the design direction calls noise rather than emphasis.
- About 200 lines of inline JSX in ChatView; the composer panel duplicates the actions with slightly different sets (the overflow with "Always allow this session" exists only in the composer).
- Coloured glowing dots (`shadow-[0_0_8px_var(--warning)]`) are decoration outside the token system.

## Remodel goals

- **Experience:** one decision surface (design direction §3.4 and §8 "Approvals and questions"), at the frontier attached to the composer: what (one sentence in the agent's words), exactly what will happen (command or path in mono, expandable to the full command or diff), and actions: Approve (primary, focused), Decline, "Decline and tell <agent>" as a secondary text action, "always allow" options behind a small menu. Questions and plans use the same surface. The scroll pill may say "Approval waiting" as navigation, not as a second copy. The decision is the view's key light; it outranks the live agent.
- **Motion — "An approval arrives" (design direction §3.4), implement as written:**
  1. **Cut to the decision (0–280 ms):** the decision surface rises 12 px and fades in at the frontier, attached to the composer; the composer's editor area cross-fades into the approval content; the composer's height animates once (`layout`, 280 ms, `spring.gentle`). A static `--light-attention` wash fades in under it over the same 280 ms.
  2. **One sweep (280–880 ms):** the surface's edge brightens once: a pseudo-element border in `--warning` fades 0 → 0.8 → 0.3 over 600 ms (`sweep` preset), then holds. Never repeats for the same request.
  3. **Focus:** keyboard focus moves to Approve if the user was not typing; otherwise focus stays and the shortcut hint appears.
  4. **Elsewhere:** sidebar row status swaps to "Needs approval" with `iconSwap` and joins the attention group; if the window is unfocused, the desktop shell sends the OS notification and badge; nothing animates in a hidden window. Mobile: a warning haptic.
  5. **Resolution (280 ms):** Approve collapses the surface into a compact log row ("Approved · create internal/store/sqlite.go") with `checkDraw`, and the editor returns; Decline the same with "Declined". Hold-to-allow fills with a linear `scaleX` tracking the hold exactly.
     Cost medium (one height layout). Reduced: instant swap, static wash, no sweep. Off: instant. No information lives only in motion.
- **Performance:** the surface subscribes to the pending-request view model, not the activity list; arrival must not re-render the timeline rows.
