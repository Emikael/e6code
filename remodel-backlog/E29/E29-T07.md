# E29-T07 · E6 Connect account, relay and cloud environments

## What it is

E6 Connect is the hosted way to reach your environments from anywhere without port forwarding or Tailscale. The user signs in to an E6 Connect account (Clerk identity) on the host and on their other devices. The host is **linked** to the account; the **relay** (a Cloudflare Worker service in `infra/relay`) provisions a **managed tunnel** (a Cloudflare tunnel connector the server runs as a child process) that gives the environment a public hostname, and brokers one-time credentials so a signed-in device can open its own session with the environment. The relay is not in the traffic path: after bootstrap, clients talk to the environment's tunnel hostname directly. The same link can instead be **publish-only**, sending agent activity to the relay for mobile push notifications and Live Activities without exposing the environment.

## When it is used

- Enabling remote access on a desktop host: Settings → Connections → E6 Connect, sign in, enable.
- A headless host: `e6 connect` (PKCE in a browser, or a device code over SSH), optionally installing the background service.
- On the phone or another browser: sign in to the same account and pick the environment from the cloud list.
- Receiving mobile notifications for agent work (Publish agent activity).
- Removing a machine: Deregister from the account page, or `e6 connect unlink` / `logout` on the host.
- Troubleshooting a link that fails (`e6 connect status`).

## How it works today

- **Client surfaces (web/desktop):**
  - `/connect` CLI authorize page (only when `connectCliAuthRoutesEnabled()`): eyebrow, heading "Connecting your terminal", description, Sign in; states incomplete link, waiting, needs sign-in, done (`components/cloud/ConnectCliAuthSurface.tsx`).
  - E6 Connect onboarding dialog after sign-in when no devices are connected: "Set up E6 Connect" with switches "Publish this environment" (managed tunnel) and "Publish agent activity" (push and Live Activities), then a device list (`ConnectOnboardingDialog*.tsx`, 359 lines).
  - Relay client install dialog when the connector binary is missing: stages Checking, Waiting for installer, Downloading, Verifying, Installing, Validating, Activating (`RelayClientInstallDialog.tsx`).
  - Cloud environment connect list, embedded in onboarding, the welcome wizard and Connections: the account's environments with connect action, compatibility errors, status dots, skeleton rows, polling while empty (`CloudEnvironmentConnectList.tsx`, 478).
  - Account: Clerk `UserButton` in the settings sidebar with custom pages "E6 Connect" (linked servers, link time, endpoint, Deregister, copy trace id) and "Mobile clients", plus a "Sign in to E6 Connect" item when signed out (`components/clerk/*`, `E6ConnectUserProfilePage.tsx` 260). Clerk appearance is mapped from theme tokens in code; Electron bundles clerk-js and supports passkeys through `@clerk/electron` (macOS needs a signed provisioning profile).
  - Connections → This machine: E6 Connect link switch and Publish agent activity (`CloudLinkRow`, `ConfiguredCloudLinkRow`, `useCloudLinkController`).
- **Server** (`cloud/http.ts`, 1,083 lines): `POST /api/connect/link-proof`, `/api/connect/relay-config`, `GET /api/connect/link-state`, `POST /api/connect/unlink`, `/api/connect/preferences`, `/api/e6-connect/health`, `/api/connect/mint-credential`, `/api/e6-connect/mint-credential`; WS `cloudGetRelayClientStatus`, `cloudInstallRelayClient`. Desired link state persisted (`CliState`) and reconciled at startup with exponential backoff up to 10 minutes. `ManagedEndpointRuntime.ts` supervises the connector with crash-loop backoff and output classification. `AgentAwarenessRelay.ts` (641) publishes aggregate agent activity (skips history imports and intent-only events to avoid a premature "Done").
- **CLI** (`cli/connect.ts` 719, `CliTokenManager.ts` 587): `e6 connect login|link|status|publish|unlink|logout` with `--headless`, `--publish-only`, `--json`, `--disable`; PKCE loopback via the hosted `/connect` page, or RFC 8628 device flow over SSH.
- **Relay** (`infra/relay`, Cloudflare Workers + Queues + Hyperdrive, PlanetScale Postgres, Clerk, APNs, FCM; deployed by `.github/workflows/deploy-relay.yml` on every push to main).
- **Behaviour to preserve (security):**
  - A relay token is never an environment login; an authenticated cloud user still needs an active environment link.
  - The relay asks the environment to mint a one-time bootstrap credential bound to the client's DPoP key; the client exchanges it directly with the environment; the relay never sees the session token, and the bootstrap credential is useless without the client's private key.
  - Mutual authentication: the environment accepts only bounded, replay-guarded relay proofs for its own identity, linked user and requested operation; signed environment responses bind the result to the request nonce (and mint responses to the client key); the relay verifies them, so another process behind the tunnel cannot impersonate the environment.
  - Managed tunnels expose only a validated loopback HTTP origin; link proofs reject forwarded authority headers; the relay resolves endpoints from its own allocations, never a caller-supplied URL; health and mint requests never follow redirects.
  - The CLI is a public OAuth client (PKCE, no secret); device flow over SSH has no redirect URI.
  - Unlink commits revocation before external teardown; release and unlink claim the allocation generation first so delayed cleanup cannot delete a reused tunnel.
  - Credential renewal does not drop healthy connections; a failed renewal affects only that request.
- **Behaviour to preserve (lifecycle and UI):**
  - Everything is disabled and hidden when the build lacks public cloud config; `e6 connect` becomes an unlisted "unavailable" stub.
  - Normal shutdown of a CLI-managed link releases the tunnel but keeps the hostname reservation and allocation (environment shows "offline", not "not authorized"); client-installed links and update handoffs keep the tunnel.
  - Connector respawn has backoff (a past bug respawned ~100/s and exhausted the V8 heap).
  - Deregister works even when the environment is offline or wiped.
  - Troubleshooting table: `environment_link_limit_exceeded` (deregister an unused one), `auth_invalid`/`invalid_bearer` (login again), expired link proof (check clock, update), HTTP 403 (relay access, proxies; keep Cloudflare Ray ID), 408/429/5xx (startup retries for up to ten minutes).
  - Mobile: Settings → E6 Account and onboarding sheet with "Don't show this again" per account (E34-T04); push and Live Activities (E35-T01).
- **Surfaces:** web, desktop, mobile, server, CLI, relay.
- **Where the code lives:** web `apps/web/src/components/cloud/*`, `components/clerk/*`, `cloud/managedAuth.tsx`, `cloud/publicConfig.ts`, `cloud/connectCliAuth.ts`, `routes/connect.tsx`, `main.tsx:47-58`; client `packages/client-runtime/src/relay/managedRelay.ts` (944), `managedRelayState.ts`, `discovery.ts`; shared `packages/shared/src/{relayAuth,relayJwt,relaySigning,relayClient,connectAuth,dpop}.ts`; server `apps/server/src/cloud/*`, `relay/AgentAwarenessRelay.ts`, `cli/connect.ts`; desktop `apps/desktop/src/app/DesktopClerk.ts`; relay `infra/relay/src/*`; contracts `packages/contracts/src/relay.ts`; docs `docs/internals/e6-connect.md`, `docs/user/remote-access.md`, `docs/operations/connect-setup.md`.

## Problems today

- The `/connect` eyebrow uses raw `text-blue-600 dark:text-blue-400` instead of semantic roles.
- Clerk's UI is a separate visual system themed through a mapping in code; Electron bundles full clerk-js.
- DPoP proof verification is duplicated between server and relay.
- The feature cannot be exercised without cloud config, so it is under-tested in normal development and was not captured.

## Remodel goals

- **Experience:** one "E6 Connect" place per client: account, this machine's link (Publish this environment, Publish agent activity), and the account's environments, with link state in words (Linked, Offline, Not authorized, Limit reached) and the troubleshooting remedy inline for each error code.
- **Motion:** relay client install stages advance with `swap` and complete with `checkDraw`; cloud list rows appear without stagger loops; no skeleton breathing beyond one stepped breath.
- **Pairing-like screens** (`/connect`) move last (architecture §5 item 4) and follow the onboarding direction (ambient light allowed, design direction §5.7).
- **Performance:** Clerk loads only when cloud config exists and only on screens that need it; it stays out of the entry bundle.
