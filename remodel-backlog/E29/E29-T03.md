# E29-T03 · Environment auth model and secrets

## What it is

The environment auth model is how every E6 server decides who may talk to it and what they may do. Each server publishes a **descriptor** saying which ways to authenticate it accepts; issues its own sessions (browser cookie, bearer token, or DPoP token bound to a client key); hands out short-lived WebSocket tickets; checks a required **scope** on every RPC; and keeps its signing keys and other secrets in the OS keychain or under `secrets/`. Cloud identity (E6 Connect) is a separate trust boundary: a relay token is never an environment login. This is server-only foundation; no screen.

## When it is used

On every HTTP request and WebSocket connection from web, desktop, mobile, CLI and relay-brokered clients; at server start (keys, policy, dev credential); in headless startup (`e6 serve` prints a pairing URL).

## How it works today

- **Entry points:** `GET /.well-known/e6/environment` (descriptor; also the desktop supervisor's readiness probe), `GET /api/auth/session`, `POST /oauth/token` (RFC 8693-style exchange), `POST /api/auth/websocket-ticket`, DPoP header on any request, every WS RPC, env `E6CODE_DEV_AUTH_TOKEN`, `e6 serve` / `e6 start`.
- **Policy and descriptor** (`EnvironmentAuthPolicy`): `desktop-managed-local`, `remote-reachable` or `loopback-browser`, derived from run mode and bind host. Bootstrap methods `desktop-bootstrap`, `one-time-token`; session methods `browser-session-cookie`, `bearer-access-token`, `dpop-access-token`; a per-instance session cookie name.
- **Scopes:** `orchestration:read`, `orchestration:operate`, `terminal:operate`, `review:write`, `access:read`, `access:write`, `relay:read`, `relay:write`. Standard client = first four plus `relay:read`; administrative = all eight.
- **RPC authorization** (`RpcAuthorization.ts`, 195 lines): a static, exhaustive method→scope table typed against `WsRpcGroup`; adding an RPC without a scope fails to compile; `device.list` raises its required scope when it can retry/install tools.
- **Secrets** (`ServerSecretStore.ts` 665, `OsKeychain.ts` 402): `<state>/secrets/<name>.bin`, optionally in macOS Keychain / Windows Credential Manager / Linux Secret Service via `@napi-rs/keyring`; keychain calls race a timeout and fall back to file so a stuck Secret Service cannot freeze startup; names sanitised; old files migrate; `selectSecretBackend` can force the file backend. Provider secrets in settings read back as `SECRET_VALUE_REDACTED`.
- **Dev credential** (`ReusableDevAuth.ts`): a fixed `E6CODE_DEV_AUTH_TOKEN` (≥ 32 chars) grants admin access across worktrees on one hostname in web dev only; session ids `dev-auth-`, cookie `e6_dev_session_<hash>`, 30-day cookie.
- **Headless startup** (`startupAccess.ts`): resolves a connection host (wildcard bind → a non-internal IPv4), mints a startup credential (`purpose: "startup"`, admin scopes, 24 h in dev) and prints connection string, token and URL.
- **Behaviour to preserve (security properties):**
  - Authority survives transport changes: pairing delegates scopes; exchange narrows, never widens; ordinary pairing never grants access- or relay-management.
  - Every RPC declares a scope; a successful socket handshake grants nothing beyond the session's scopes.
  - DPoP binds a token to the client's proof key; an invalid proof fails and never falls back to bearer; proof replay is recorded in the DB and failures map to specific `DpopFailureReason`s clients react to.
  - Bearer and DPoP clients get WebSocket tickets (one-time, 5-minute default, bounded in-memory replay set) so long-lived tokens never appear in socket URLs; browsers use tickets for `<img>`/WS where headers cannot be set.
  - Cookie-authenticated upgrades and state-changing requests require a trusted `Origin`: this server's endpoint, the dev UI, `e6code://app` / `e6code-dev://app`, the hosted app when E6 Connect is enabled, `E6CODE_DEV_ALLOWED_ORIGINS`; `Sec-Fetch-Site` must be `same-origin` for endpoint and dev-origin matches; a Tailscale hostname is trusted only if it is this machine's own MagicDNS name. Bearer, DPoP and ticket clients may omit `Origin`.
  - Cookies are host-only and not port-scoped, so cookie names are unique per server instance (`resolveSessionCookieName`); legacy names are still honoured.
  - The dev credential is ignored by desktop and non-development servers; a rejected normal credential never falls back to it; rotating it invalidates its tickets; each worktree keeps its own DB, keys and revocation.
  - Keychain failure degrades to file storage, never to no storage and never to a hung start.
  - `orchestration:read` permits reading files the server account can read (the environment, not the project, is the filesystem boundary); signed asset URLs are bearer credentials for one file identity.
- **Surfaces:** server; consumed by web, desktop, mobile, CLI and relay.
- **Where the code lives:** `apps/server/src/auth/EnvironmentAuth.ts` (1,261), `EnvironmentAuthPolicy.ts`, `http.ts` (500), `SessionStore.ts` (1,147), `PairingGrantStore.ts` (578), `cookieOrigin.ts` (385), `dpop.ts`, `RpcAuthorization.ts`, `ServerSecretStore.ts`, `OsKeychain.ts`, `ReusableDevAuth.ts`, `utils.ts`, `requestUrlRedaction.ts`, `startupAccess.ts`, `apps/server/src/persistence/AuthSessions.ts`; contracts `packages/contracts/src/auth.ts`, `environmentHttp.ts`; client `packages/client-runtime/src/authorization/*`, `packages/shared/src/{dpop,dpopCommon,oauthScope}.ts`; docs `docs/internals/environment-auth.md`.

## Problems today

- DPoP verification logic is duplicated between the server and the relay (`infra/relay/src/auth/DpopProofs.ts`), not shared.
- Many error types and ordering rules make the area XL in complexity; the internal doc is the best spec besides the tests.

## Remodel goals

- **No behaviour change.** Architecture §5 item 4 puts this machinery out of scope for the UI rewrite; this task exists so the parity list is explicit and so any v2 client work (E04-T04) consumes it unchanged.
- Optional, separately reviewed: share one DPoP verification implementation between server and relay.
- Keep the method→scope table exhaustive as RPCs are added by v2 features.

## Done when

- [ ] A security regression suite exists (or is confirmed) covering each property above: narrowing-only exchange, scope per RPC, DPoP no-fallback and replay, ticket one-time use and expiry, Origin and `Sec-Fetch-Site` rules, cookie-name uniqueness, dev-credential isolation, keychain timeout fallback.
- [ ] Every RPC added by M1-M5 work has a scope entry (compile-time check still enforced).
- [ ] Connection modes verified against a server built from the rewritten tree: local desktop, LAN, tailnet, relay, SSH forward, hosted web.
- [ ] Any shared DPoP extraction has its own PR and keeps relay and server tests green.
