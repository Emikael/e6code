# E29-T08 · Load balancing across environments

## What it is

Load balancing ("Auto balance") spreads new threads across machines. When a project exists on two or more connected environments (grouped across environments in the sidebar), a new draft can start on whichever machine currently has the most free CPU and memory, weighted by a per-machine preference: Normal, Prefer, Less often or Manual only. It is off by default and the preferences are saved in each client.

## When it is used

- A user with a laptop and a desktop both cloned to the same repository wants new agent work to land on whichever machine is idle.
- A user marks the laptop "Less often" so it stays cool, or "Manual only" to keep it out of automatic placement.

No screenshot: the section appears only with two or more enabled environments; the capture had one.

## How it works today

- **Entry points:** Settings → Connections → Load balancing (shown once two or more machines are switched on): enable switch plus a preference per machine; the composer's environment control offers "Auto balance" for new drafts (E23-T01).
- **Storage:** client settings `loadBalancingEnabled` (default false) and `loadBalancingWeights` (record of environment key → integer 0 to 100; the UI maps Normal, Prefer, Less often and Manual only onto these values).
- **Behaviour to preserve:**
  - Applies only to new threads in projects grouped across connected environments; existing threads stay where they started.
  - The composer checks eligible machines when choosing a draft's environment, then keeps that choice stable; choosing Auto balance again re-checks resources; choosing a machine, branch or worktree pins the draft to that machine.
  - Preferences are preferences, not traffic percentages.
  - If resource checks are unavailable or every eligible machine is full, the user must pick a machine manually.
  - Mobile keeps manual environment selection.
- **Surfaces:** web and desktop; server supplies resource readings (resource telemetry).
- **Where the code lives:** `apps/web/src/components/settings/LoadBalancingSettings.tsx` (134 lines); placement in `apps/web/src/composerDraftStore.ts` and `components/ChatView.tsx`; contracts `packages/contracts/src/settings.ts` (`LoadBalancingWeights`); docs `docs/user/remote-access.md` ("Balance new threads across machines").

## Problems today

- Placement logic lives in the legacy composer store and ChatView, not in `client-runtime`, so mobile cannot reuse it.
- The user cannot see why a machine was chosen.

## Remodel goals

- **Experience:** the composer's environment chip says why ("Auto · studio has most free memory"); settings show each machine's current load in words next to its preference.
- **Structure:** move placement into `client-runtime` as a pure function over resource readings and weights so mobile can adopt it later.
