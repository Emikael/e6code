# E29-T02 · Pairing links and authorized clients

## What it is

Pairing is how a new device gets access to an environment. The host creates a **pairing link**: a short-lived, one-time credential, shown as a URL and a QR code, that carries a set of **scopes** (permissions). A phone or browser that opens it exchanges the credential for its own long-lived **session**. The host can list pairing links and client sessions ("authorized clients") and revoke them individually or revoke all other clients at once. The same model powers `e6 pair` on the command line and the startup URL printed by `e6 serve`.

## When it is used

- Adding a phone: Settings → Connections → Create pairing link, scan the QR in the mobile app (Settings → Environments → Add environment).
- Opening a remote server in a browser for the first time: paste the URL, which lands on `/pair#token=…`.
- A headless server: `e6 pair` prints a fresh QR and URL; `e6 auth pairing create|list|revoke` and `e6 auth session issue|list|revoke` manage access from a shell.
- A device is lost: revoke its session. A link was shared by mistake: revoke the unused link.

## How it works today

- **Entry points:** Settings → Connections → Authorized clients (Create pairing link, link rows with QR, client rows, revoke, "Revoke others"); `/pair#token=…` and hosted pairing URLs; mobile Add environment (QR scan or paste); CLI `e6 pair [--ttl] [--label] [--tailscale] [--tailscale-serve-port]`, `e6 auth pairing …`, `e6 auth session …`, `e6 serve` startup URL. HTTP: `POST /api/auth/pairing-token`, `GET /api/auth/pairing-links`, `POST /api/auth/pairing-links/revoke`, `POST /api/auth/browser-session` (redeem), `GET /api/auth/clients`, `POST /api/auth/clients/revoke`, `POST /api/auth/clients/revoke-others`; WS stream `subscribeAuthAccess` keeps the list live.
- **Create pairing link dialog:** a label and a scope checklist, defaulting to the standard client scopes; at least one scope required:

| Checkbox         | Scope                   | Default | Description shown                              |
| ---------------- | ----------------------- | ------- | ---------------------------------------------- |
| View environment | `orchestration:read`    | on      | Read threads, status, diffs, and configuration |
| Operate tasks    | `orchestration:operate` | on      | Start tasks and perform changes                |
| Use terminals    | `terminal:operate`      | on      | Create terminals and send input                |
| Write reviews    | `review:write`          | on      | Create comments while reviewing changes        |
| View relay       | `relay:read`            | on      | Inspect managed relay connectivity             |
| View access      | `access:read`           | off     | Inspect pairing links and authorized clients   |
| Manage access    | `access:write`          | off     | Issue and revoke credentials for other clients |
| Manage relay     | `relay:write`           | off     | Change managed tunnel connectivity             |

- **Link row / popup:** QR code, an endpoint selector choosing which advertised address the URL uses (LAN IP, Tailscale HTTPS name, hosted-app link), copy token or URL, scope summary ("5 scopes"), revoke. **Client rows:** label, client metadata (IP, user agent), created/last seen, scopes, revoke; the current session cannot revoke itself.
- **Behaviour to preserve (security):**
  - Pairing credentials are one-time by default (bounded-use counts exist; desktop bootstrap is "unbounded") and short-lived: server default TTL 5 minutes; dev startup and desktop bootstrap 24 hours; `--ttl` overrides on the CLI.
  - What a pairing link grants is exactly its scopes. Ordinary pairing never grants `access:*` or `relay:write`; the startup/administrative bootstrap grants all eight. Exchanging a credential can narrow but never widen the grant. Creating a link requires `access:write` **and** every scope being delegated.
  - The access list contains metadata only, never a recoverable pairing secret; the raw credential is returned only in the creation response. Therefore a link's URL can be copied only from the client that created it, while its Connections page stays open; after reload, create a new link.
  - The pairing secret travels in the URL **fragment** (`#token=`), never the query, so it never reaches the hosted origin or server logs; request URLs are redacted in logs; the browser strips it from history after exchange.
  - Redeemed sessions: browser cookie, bearer token or DPoP-bound token (E29-T03); default session TTL 30 days.
  - Revoking an unused link prevents new pairings; revoking a session removes that device's access; "Revoke others" revokes every session except the caller's; self-revoke is refused. Revocation persists across restart.
  - A session with an open connection stays listed after its access credential expires.
  - Client labels and device metadata have no authorization role.
  - Desktop restarts replace the previous local bearer for the same subject (transactional; a failed replacement leaves the old credential usable); pairing and browser sessions do not follow this rule.
  - Treat pairing URLs as passwords: never shown in screenshots, logs, analytics or bug reports.
- **Behaviour to preserve (UI):** Authorized clients appears only when the environment is remotely reachable and the session has `access:read`; endpoint selector never falls back to loopback silently; list updates live via `subscribeAuthAccess`.
- **Surfaces:** server, web, desktop, mobile (redeem side), CLI.
- **Where the code lives:** server `apps/server/src/auth/PairingGrantStore.ts` (578 lines), `auth/SessionStore.ts` (1,147), `auth/EnvironmentAuth.ts` (1,261), `auth/http.ts` (500), `auth/requestUrlRedaction.ts`, `startupAccess.ts`, `cli/pair.ts` (542), `cli/auth.ts`; web `components/settings/ConnectionsSettings.tsx` (`PairingLinkListRow` line 591, `ConnectedClientListRow` 976, create flow about 1056-1100, `PAIRING_SCOPE_OPTIONS` 208), `pairingUrls.ts`, `hostedPairing.ts`; contracts `packages/contracts/src/auth.ts` (`AuthStandardClientScopes`, `AuthAdministrativeScopes`); docs `docs/internals/environment-auth.md`, `docs/internals/remote.md`.

## Problems today

- Scope names are shown as raw `orchestration:read` codes in summaries; the checklist wording is clearer than the summary.
- The pairing URL disappears when the page reloads; users who navigate away mid-share are confused (docs explain it, the UI barely does).
- QR and endpoint logic live inside the 3,779-line connections file.

## Remodel goals

- **Experience:** a "Pair a device" flow: pick what the device may do (presets "Standard" and "Administrator" plus custom), pick the address the device can reach (with a plain warning when only loopback is available), then show a large QR and URL with a visible expiry countdown in words. The client list reads as devices ("iPhone · last seen 2 min ago · Standard access").
- **Motion:** QR reveal uses `reveal`; revoke collapses the row with `layout`; expiry is static text updated once per second, not an animated ring.
- **Never** cache or persist the raw credential in client state, storage, analytics or crash reports.
