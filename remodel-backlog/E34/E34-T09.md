# E34-T09 · Mobile project favicons, provider icons and machine symbols

## What it is

The small identity marks that recur across the mobile app: a **project favicon** (the repository's own favicon, fetched from the server, with a folder fallback), **provider icons** (Claude, Codex, Cursor, Grok, OpenCode, Antigravity marks next to models and threads), **environment machine symbols** (a glyph for the kind of machine an environment runs on: server, cloud VM, Linux/WSL, desktop, laptop, mini PC, workstation), **source-control icons** (GitHub, GitLab and others), **file-type icons** (Pierre icon set in trees and file chips), and the **E6 brand mark and wordmark**. All UI glyphs go through `AppSymbol`, which takes SF-Symbol-style names and renders SF Symbols on iOS and Tabler icons on Android.

## When it is used

Everywhere: Home thread rows and project groups, the tablet sidebar, the new task project list, the environment list, model pickers, git and PR rows, file trees and file chips. Users rely on the favicon and machine glyph to tell projects and machines apart at a glance.

## How it works today

- **Entry points:** none of its own; rendered by other screens. The machine kind is chosen on the server or from web/desktop (Settings > Connections, `environmentIcon`, E29-T10); mobile only displays it.
- **Behaviour to preserve:**
  - Project favicon URL is resolved per environment and workspace root (`projectFaviconUrlAtom`, `@e6tools/shared/projectFavicon`); inline `data:` images and signed remote URLs are cached on disk with keys that survive token rotation but reset when the icon changes (`projectFaviconCache.ts`); the folder icon is the fallback (open or closed variant) while loading or on failure, matching web's folder icon.
  - Favicons are part of the offline cache (`favicon` records in Client Storage, E34-T08).
  - Provider icons are drawn with `react-native-svg`, except Antigravity which uses a bundled PNG (`assets/antigravity.png`).
  - Machine symbols map each `EnvironmentMachineKind` to an SF Symbol name and an accessible label ("Server", "Cloud VM", "Linux/WSL", "Desktop", "Laptop", "Mini PC", "Workstation").
  - `AppSymbol` (about 95 importing files) maps SF-Symbol names to Tabler icons on Android through per-icon deep imports, so Metro does not register the whole Tabler set; `expo-symbols` renders on iOS. One pull-request glyph uses Tabler on iOS too.
  - File-type icons come from the Pierre PNG set shipped inside the `e6-markdown-text` module (about 60 PNGs), synced with `sync:pierre-icons`.
- **Surfaces:** web's project identity (E11-T06) also supports a user-chosen icon (a Lucide name with a colour, stored on the server) and a monogram, plus a favicon picker; mobile shows only the favicon or folder fallback (not verified whether a stored custom icon is ignored or unsupported on mobile). Web's provider marks live in `components/Icons.tsx`. The icon layer decision (Phosphor replacing Lucide, Android possibly moving from Tabler to the same artwork) is E03-T01 and E03-T02.
- **Platform differences:** iOS renders SF Symbols (`AppSymbol.ios.tsx`, `expo-symbols`) in monochrome or hierarchical modes; Android renders Tabler icons (`AppSymbol.tsx` with `AppSymbol.tabler.d.ts` mapping), with some names given per platform (for example `folder.fill` on iOS and `folder` / `folder_open` on Android).
- **Where the code lives:** `apps/mobile/src/components/ProjectFavicon.tsx` (145), `projectFaviconCache.ts` (94), `ProviderIcon.tsx` (140), `EnvironmentMachineSymbol.tsx` (39), `SourceControlIcon.tsx` (123), `PierreEntryIcon.tsx`, `AppSymbol.tsx` (301), `AppSymbol.ios.tsx`, `AppSymbol.tabler.d.ts`, `BrandMark.tsx`, `E6Wordmark.tsx`, `apps/mobile/assets/antigravity.png`, `apps/mobile/modules/e6-markdown-text` (Pierre PNGs).

## Problems today

- Two icon vocabularies (SF Symbols names and Tabler) are bridged by a hand-maintained map; adding a glyph means editing the map and checking both platforms.
- Machine labels differ from their symbol names ("mac-mini" shows "Mini PC"), which is deliberate but easy to break.
- Custom project icons chosen on web do not appear on mobile, so the same project can look different on each client.

## Remodel goals

- **Experience:** one semantic icon registry shared with web (architecture 2.5): mobile's `AppSymbol` names become semantic names mapped to SF Symbols on iOS and to the chosen artwork on Android. Projects look the same on every client, including custom icons through the permanent Lucide-name map (design direction 6.5). Provider marks render monochrome in dense rows and in brand colour only in model pickers (design direction 6.4).
- **Performance:** keep per-icon imports on Android and disk-cached favicons; no icon font or full-set registration.

## Done when

- [ ] `AppSymbol` reads from the shared semantic registry; a lint rule prevents direct icon-library imports outside it.
- [ ] Favicon caching, fallback and offline behaviour preserved; custom project icons decided and, if supported, rendered through the Lucide-name map.
- [ ] Provider, source-control and machine marks drawn to the shared grid, monochrome in dense UI, with accessible labels.
- [ ] Android icon artwork follows the D2b decision (Tabler kept or Phosphor adopted).
- [ ] Icons checked in dark and light on both platforms at the sizes used in lists.
