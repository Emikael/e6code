# E34-T06 · Mobile server settings pages

## What it is

Four mobile settings pages edit settings stored on the **server** (in each environment's `settings.json`), not on the phone: **New threads**, **Source control**, **Agent behavior** and **Maintenance**. One component renders all four. They write to the environments chosen in the Settings header filter and, when a project is selected there, to that project's overrides. This is the phone's subset of what web shows in Settings > General, Source control and Integrations.

## When it is used

- Making new threads start in a fresh worktree by default, or with a stricter permission mode, from the phone.
- Turning on automatic pull of the default branch, or making new worktrees start from the latest origin.
- Changing how replies stream (whole answer, paragraph by paragraph, or token by token), allowing the agent to control the preview browser, or routing turns through Jev.
- Turning provider update checks on or off, and whether threads continue after a server restart or update.

Layout in words: each page is a grouped list titled with the page name, under the same environment filter header as the rest of Settings. Choice rows show a label and a one-line description with a check on the selected value; switch rows show a label and a switch. When a project is selected in the filter, a "Project" section at the top offers "Use defaults" to clear this page's project overrides.

- **New threads** (`settings/new-threads`): "Default workspace" with "Current checkout — Start new threads in the existing workspace." and "New worktree — Give each new thread a separate checkout."; "Default permissions" with the runtime modes (Supervised, Auto-accept edits, Auto, Full access).
- **Source control** (`settings/source-control`): "Default branch" with "Automatically pull"; "Worktrees" with "Start from origin".
- **Agent behavior** (`settings/agent-behavior`): "Response streaming" with "After the turn — Show the answer when the agent finishes.", "Finished paragraphs — Show each paragraph or code block as it completes." and "Token by token (legacy) — Repaint for every token; this can be slower." (choosing it asks "Use legacy token streaming?" with "Use token streaming"); "Preview browser" with "Agent browser access"; "Route turns through Jev" with a secure "Jev API key" field.
- **Maintenance** (`settings/maintenance`): "Updates" with "Check provider updates" and "Continue after restart".

## How it works today

- **Entry points:** Settings index > Server settings section; deep links `settings/new-threads`, `settings/source-control`, `settings/agent-behavior`, `settings/maintenance`.
- **Behaviour to preserve:**
  - All values are server settings. Writes fan out to every selected, connected environment (`planMobileScopedSettingsPatch`), counted as pending until all finish; controls are disabled while writing and when no selected environment is connected.
  - Project-scopable keys per page (`PAGE_PROJECT_KEYS`): New threads (`defaultThreadEnvMode`, `defaultRuntimeMode`), Source control (`defaultAutoPull`, `newWorktreesStartFromOrigin`), Agent behavior (`responseStreamingMode`, `enableAgentBrowserAccess`), Maintenance (`continueThreadsAfterServerUpdate`). Other rows (Jev routing, provider update checks) are environment-only and are disabled when a project is selected.
  - Project overrides need the server capability `projectSettingsOverrides`; "Continue after restart" needs `threadRestartContinuation`. Missing capabilities disable the row rather than hide it (not verified for every row).
  - Token streaming requires an explicit confirmation.
  - The Jev API key is write-only (entered in a secure field, never read back).
- **Surfaces:** web and desktop (E25-T05, E25-T07, E25-T08, E25-T09, E15-T06, E25-T12) expose many more server settings: default model and text-generation model, "Add project starts in", merge method, git fetch interval, source-control writing style and writer model, background activity profile, storage and worktree cleanup, browser and device integrations, provider instances. Web shows "Mixed" values and inheritance badges (default, environment, project, checkout); mobile shows the current value of the selection without an inheritance marker (not verified for mixed values). Server: settings service (E25-T04).
- **Platform differences:** iOS uses native grouped lists with checkmark rows and UISwitch; Android uses Material radio-style rows and `MaterialSwitch`, with `AndroidSettingsEnvironmentFilter` in its header. The token-streaming confirmation is a native alert on both.
- **Where the code lives:** `apps/mobile/src/features/settings/SettingsServerControlsRouteScreen.tsx` (537; `PAGE_TITLES`, `PAGE_PROJECT_KEYS`, `ServerSettingsDetail`), `settings-scoped-server.ts`, `settings-environment-filter.tsx`, `components/SettingsProjectOverridesSection.tsx`.

## Problems today

- One component switches on the page id to render four unrelated pages; adding a setting means touching shared conditionals.
- Mixed values across environments are not shown the way web shows them, so writing to "all environments" can silently overwrite different values.
- Which server settings exist on mobile is an ad hoc subset, not a stated policy.

## Remodel goals

- **Experience:** state a policy for which server settings belong on the phone (what someone changes away from the desk), show "Mixed" when selected environments disagree, and mark project overrides clearly. Describe consequences in plain words (as the streaming descriptions already do).
- **Motion:** none beyond native controls; a write across several environments shows a quiet per-environment result only on failure.
- **Performance:** pages render from cached server config instantly and stay usable while offline (read-only with a clear "offline" word).

## Done when

- [ ] All nine settings above read and write correctly for one environment, several environments and a project, with capability gates.
- [ ] Mixed values across environments are shown and resolved deliberately.
- [ ] The mobile server-settings subset is a recorded decision, aligned with web's settings structure (E25-T01).
- [ ] Token-streaming confirmation and write-only Jev key preserved.
- [ ] Shared tokens in dark and light on both platforms; tests for scoped writes kept.
