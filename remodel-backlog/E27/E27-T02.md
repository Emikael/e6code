# E27-T02 · Provider install, update and auth

## What it is

Provider CLIs (Codex, Claude Code, Cursor, Grok, OpenCode) are installed and signed in outside E6 Code, but the app watches their versions and can update them in place: when a newer CLI version exists, the provider shows "Update available" with the command to run, and, where the server can tell how the binary was installed, an "Update now" button that runs the owning installer on the environment. Behind it sit three server flows: provider auth (start, complete, cancel, log out), provider install (download, cancel, remove a managed runtime) and provider maintenance (update). Only Antigravity implements in-app auth and install today (E27-T04); the others report "run the CLI's login" guidance.

## When it is used

- A provider prints a "newer version available" notice, or a feature needs a newer CLI (OpenCode 2.0.12+, Codex async questions).
- An update toast appears after the background check, and the user clicks Update now or dismisses it.
- A user on a remote server updates a CLI without opening a shell on that machine.
- A user turns off provider update checks on General.

## How it works today

- **Entry points:** Providers list row (update-available icon), the instance editor (advisory with copyable command and inline run-update button), provider update toasts (dismissible; dismissed keys stored in `dismissedProviderUpdateNotificationKeys`), General → "Provider update checks" (server setting `enableProviderUpdateChecks`). RPCs: `server.updateProvider`; `provider.auth.*` (start, complete, cancel, logout, subscribe stream); `provider.install.*` (start, cancel, subscribe, remove).
- **Server:** the provider snapshot carries `versionAdvisory` (current, latest, suggested command, whether the environment can run the update). `providerMaintenance.ts` (723 lines) resolves how the binary was installed (npm global, Homebrew, standalone Codex, native self-update) and runs the owning update command through `ProviderMaintenanceRunner` with a command coordinator (one update at a time per provider) and cached "latest version" checks. Auth and install delegate to per-instance controllers; only Antigravity provides them.
- **Behaviour to preserve:**
  - Update checks run only when `enableProviderUpdateChecks` is on (server, General page).
  - When the install method cannot be detected, only the copyable command is shown, never a button that would fail.
  - An update in progress shows progress and its result; failure shows the command output summary and leaves the old binary working.
  - Dismissing an update toast hides it for that version only.
  - Auth and install streams are per instance and cancellable.
  - Per-provider sign-in: Codex `codex login`, Claude `claude auth login` (or API key / router env vars), Cursor `agent login`, Grok `grok login` or `GROK_API_KEY`, OpenCode `opencode auth login` plus server password, Antigravity in app (capability matrix, E37-T11).
  - Mobile: General-equivalent "Check provider updates" toggle exists (mobile Maintenance page); no update button.
- **Surfaces:** web, desktop, server; mobile toggle only.
- **Where the code lives:** web `ProviderInstanceCard.tsx` (917 lines), `providerStatus.ts`, `ProviderSettingsPanel.tsx`; server `apps/server/src/provider/Layers/ProviderAuthService.ts`, `providerInstallation.ts`, `providerMaintenance.ts`, `providerMaintenanceRunner.ts`, `providerMaintenanceCommandCoordinator.ts`, `providerUpdateSettings.ts`, `cliAuthFormat.ts`.

## Problems today

- Sign-in is text-only for five providers; the user is told to leave the app and run a command on the right machine, which is hard when the environment is remote.
- Update prompts appear in three places (list icon, editor, toast) with different wording.
- The generic auth and install interfaces exist but have one implementation, so their shape is untested against a second provider.

## Remodel goals

- **Experience:** one "Update" status mark per instance with a single action; the same state drives the toast and the update notice area (E12-T05). For CLI-login providers, show the exact command for the selected environment and a copy button, and where the environment has a terminal, offer "Open terminal on vm with this command" (decision for the maintainer).
- **Motion:** update progress uses a determinate hairline that tracks real progress (`ease.linear`); completion swaps the status mark with `iconSwap`. No spinners without a label.
- **Remote:** every action works from a remote client over a tunnel; nothing assumes the client is on the provider's machine.

## Done when

- [ ] Update available, update running, update failed and up-to-date states exist for each install method, with the button shown only when the method is detectable.
- [ ] Toast dismissal per version, the General toggle and the cancel paths are preserved and tested.
- [ ] Auth and install RPC streams keep their contracts (shipped clients decode them).
- [ ] Per-provider sign-in guidance matches the capability matrix (E37-T11).
- [ ] Verified from a remote client against an environment on another machine.
