# E20-T01 · Terminal drawer and panel surface

## What it is

An interactive shell in the thread's workspace, shown in two places: a resizable **drawer** at the bottom of the chat column, and as a **Terminal tab** in the right panel. Each thread can have several terminals, arranged in groups that can be split side by side or stacked (up to four per group). Terminals run on the environment server, so they survive reloads and can be reattached from another client. This task is the drawer, the panel surface, groups and splits, and the terminal lifecycle in the UI; the rendering engine is E20-T02 and the server PTY manager is E20-T04.

## When it is used

- Running tests, a dev server or git commands next to the agent without leaving the app.
- Running a project script (E23-T11), which opens in a terminal with the right working directory and environment.
- Watching a long-running process while chatting; keeping a terminal beside the diff in the panel.
- Install and sign-in flows for providers that open a terminal with a command ready.

## How it works today

- **Entry points:** `terminal.toggle` (`mod+j`) and the title-bar terminal toggle (`PanelLayoutControls`); "T" in the panel launcher; `terminal.new` (`mod+n` when the terminal is focused), `terminal.split` (`mod+d`), `terminal.splitVertical` (`mod+shift+d`), `terminal.close` (`mod+w`) — all with `when: terminalFocus`; project scripts; RPCs `terminal.open|attach|write|resize|clear|restart|close`, `subscribeTerminalEvents`, `subscribeTerminalMetadata`.
- **Behaviour to preserve:**
  - **Drawer:** resizable height by a drag handle, persisted per thread (`terminalUiStateStore`, localStorage `e6code:terminal-state:v1`, version 4) with the thread's terminal ids, groups and active terminal; hidden/shown without killing sessions.
  - **Groups and splits:** horizontal and vertical splits, at most `MAX_TERMINALS_PER_GROUP = 4` per group; at the limit the split actions are disabled with a reason; action labels include the shortcut ("Split Terminal Horizontally (⌘D)").
  - **Panel surface:** a `terminal:<id>` surface carries its own `terminalIds`, `activeTerminalId` and `splitDirection`; store actions `openTerminal`, `splitTerminal`, `activateTerminal`, `closeTerminal`. Rendered by `ThreadTerminalDrawer mode="panel"` through `PersistentThreadTerminalPanel`.
  - **One PTY, one viewport:** a terminal id shown in the panel is excluded from the drawer, and ids are cross-checked so two viewports never attach to one PTY session.
  - **Close:** confirmation "Close terminal "<label>"? This stops the running process and clears its history." (or "Close N terminals?" listing labels), destructive variant, through `localApi.dialogs.confirm`; only one confirmation pending at a time. Whether the plain-browser build asks is not verified (the helper returns "yes" when no local API exists).
  - **Exit:** "Process exited" / "Terminal closed" is written into the terminal and the exited session closes its pane; attaching to an already-exited session still runs exit handling.
  - **Labels:** "Terminal N" by default (`getTerminalLabel`), or the running child command from server metadata; listening ports detected per terminal are shown as hints (server PortScanner).
  - **Launch context:** cwd (workspace or worktree) and environment for project scripts; provider-aware env (Codex/Claude homes) applied on the server.
  - **Persistence across reloads:** sessions live on the server; on reattach the client replays the retained history (bounded, E20-T04) with replies suppressed.
  - **Keyboard:** clear shortcut sends form feed; delete shortcuts send the right sequences; `mod+w` and `mod+t` route by `terminalFocus`.
  - **Mounting:** one drawer stays mounted per mounted thread (`mountedTerminalThreadRefs`), so switching back is instant.
- **Surfaces:** web and desktop; mobile has its own Terminal route with sessions menu, project scripts, a key accessory bar and native libghostty rendering (`09:S-18`, E33-T04); server PTY manager (E20-T04).
- **Where the code lives:** `apps/web/src/components/ThreadTerminalDrawer.tsx` (1720 lines; `TerminalViewport` ~336, drawer ~1051), `ChatView.tsx` (~949, ~998-1069, ~1290, ~1328 `PersistentThreadTerminalPanel`, ~1458, ~2096, ~10142), `terminalUiStateStore.ts` (781), `rightPanelStore.ts` (terminal surface actions), `types.ts` (`MAX_TERMINALS_PER_GROUP`), `lib/terminalCloseConfirm.ts`, `state/terminalSessions.ts`, `state/terminal.ts`, `packages/client-runtime/src/state/terminalOutput.ts` (client buffer 512 KiB).

## Problems today

- Two parallel terminal-state models: drawer groups in `terminalUiStateStore` and panel groups inside right-panel surfaces, with id cross-checks to avoid collisions.
- One persistent drawer is mounted for every mounted thread; with many threads open that is many idle canvases and subscriptions.
- 1720-line component; the terminal theme is read from computed CSS variables at runtime.

## Remodel goals

- **Experience:** one terminal model for a thread: a terminal is a session that can be shown in the drawer or in the panel (moving it between them keeps the session), never both. Group and split controls are visible, labelled and keyboard reachable. The terminal follows the theme's terminal roles (design direction §8).
- **Motion:** the drawer follows the §3.8 rule vertically: the chat column's height is committed once, then the drawer dollies up 24 px (280 ms, transform only) and closes the same way in reverse; resizing is 1:1. The terminal canvas itself is never animated, and terminal output is on the instant list (§3.10).
- **Performance:** keep the canvas engine (E20-T02). Mount canvases only for visible terminals and keep hidden sessions as data, so idle threads cost nothing; budget: no animation frames from hidden terminals, output throughput unchanged at 1 MB/s bursts.
