# E26-T02 · Theme system: built-ins and halves

## What it is

The theme system is the model under every colour in E6 Code. A **theme** is a named set of values for 60 semantic **colour roles** (canvas, chrome, toolbar, surface variants, text, border, accent, status colours, merged, message, code, sidebar and terminal roles), with a light variant, a dark variant or both. The stock "E6 Code" palette (Porcelain in light, Slate in dark) has an accent choice; five built-in themes (E6 Chat, Grove, Ocean, Ember, Iris) ship with it; users add custom and imported themes (E26-T03, T04) and servers can publish themes (E26-T05). **Halves** let a user wear one theme in light mode and another in dark mode. The same palette data feeds web CSS variables, the desktop window colours and the mobile app's generated themes.

## When it is used

- On every paint: each component's colour is a role variable.
- When the user changes theme, appearance mode or accent (E26-T01, palette, keybindings).
- When the OS switches light/dark and the user follows the system.
- When mobile builds regenerate their themes from `packages/shared`.
- When the v2 design language adds plane and light roles (design direction §4.1): this task carries those roles into every theme.

## How it works today

- **Entry points:** `hooks/useTheme.ts` (`setTheme`, `setAppearanceMode`), Appearance cards and library, command palette "Change theme"/"Change appearance", keybindings `theme.select` and `appearance.cycle`, `index.html` boot script, desktop `setTheme` IPC.
- **Data model** (`packages/shared/src/themePalettes.ts`, 1,079 lines): `BUILT_IN_THEME_IDS = ["e6-chat","grove","ocean","ember","iris"]`; `THEME_COLOR_ROLES` (60 roles); `ThemeDefinition { id, label, appearance, colors, variants?, collection?, sidebarArtwork?, managed? }`; `E6_CODE_LIGHT_THEME_COLORS` / `E6_CODE_DARK_THEME_COLORS` for the stock palette; `STOCK_ACCENT_PALETTES` (Iris, Cobalt, Rose, Graphite, each with light and dark `primary`, `primaryForeground`, `primaryHover`, `primaryEdge`, `primaryText`, `merged`, `mergedForeground`, contrast-checked at 4.5:1). Colours are stored as opaque OKLCH tokens.
- **Reserved ids:** `RESERVED_THEME_IDS` (`system`, `light`, `dark`, every built-in, legacy aliases `e6-chat-dark`, `e6-grove`, `e6-ocean`, `e6-ember`, `e6-iris`) and `UNPUBLISHABLE_THEME_IDS` (adds mobile's `e6-code`). The client library and the server publish path both consult them.
- **Web application:** palettes apply as CSS variables on `html[data-theme-id]`; per-theme blocks live in `apps/web/src/index.css` (2,296 lines, about lines 575-730); accent variables are derived from the palette (`deriveThemeAccentVariables` in `apps/web/src/themePalette.ts`, 1,816 lines); `completeThemeColors` fills missing roles; `canonicalThemePreference` maps legacy ids.
- **Preferences:** localStorage `e6code:theme` (selected id), `e6code:theme-appearance-mode`, `e6code:theme-halves:v1`, legacy `e6code:theme-follow-system`; custom library `e6code:themes:v1`.
- **Behaviour to preserve:**
  - Five built-ins plus stock, each with light and dark; halves can mix themes; single-appearance themes pin their half.
  - Accent applies to the stock theme only.
  - Legacy ids in older saves resolve to current built-ins.
  - A published or imported theme can never take a reserved id.
  - Storage failures degrade to defaults without breaking render.
  - Built-ins may render sidebar artwork only when `sidebarArtwork` is set.
  - Merged pull-request hue per palette is chosen clear of accent and status hues (comment in `themePalettes.ts`); every built-in meets 4.5:1 text and 3:1 icon contrast on its surfaces.
  - Mobile: same palettes via `generate-uniwind-themes.mts` into generated uniwind themes; mobile adds `e6-code` as an explicit default id and Material You on Android (E31-T06).
  - Desktop: `resolveDesktopTheme` feeds native window and title bar colours (E30-T01).
- **Surfaces:** web, desktop, mobile (shared data), server (only for published themes, E26-T05).
- **Where the code lives:** `packages/shared/src/themePalettes.ts`, `apps/web/src/themePalette.ts`, `apps/web/src/hooks/useTheme.ts`, `apps/web/src/index.css`, `apps/web/index.html` (boot palette copy, about line 52), `apps/mobile` theme generator and `lib/mobileTheme*.ts`.

## Problems today

- Colour values live in three hand-synced places: `index.css`, `themePalettes.ts` and the boot script in `index.html` (architecture 2.6).
- The role list mixes product areas (sidebar rows, terminal scrollbars, toolbar controls) with generic roles, and has no notion of planes or elevation, so all three panels render at the same brightness (design direction §1).
- Theme state is split between localStorage keys and client settings (`stockAccent`), with legacy keys still read.
- Complexity XL per report 05; about 9.7k lines across the theme files.

## Remodel goals

- **One source:** the design-token pipeline (`packages/design-tokens`, E01-T06, with names and values from E01-T07) owns role names and the stock/built-in values and generates web CSS, the mobile uniwind themes, Electron window colours and the boot palette.
- **New roles are derived, never required.** The Key Light roles (`--plane-ground`, `--plane-stage`, `--plane-well`, `--plane-raised`, `--plane-float`, `--edge-subtle`, `--edge-strong`, `--light-key`, `--light-attention`, `--light-rim`, `--scrim`) are computed from existing roles with `color-mix` by default (design direction §4.1, decision D8). A theme may override a derived role but never has to.
- **What happens to existing themes:** custom themes in `e6code:themes:v1`, imported VS Code themes and server-published theme files keep loading with no migration and no rewrite of stored data. They get planes and light washes from the derivation. Built-ins are re-mapped onto planes by the pipeline (E01-T11 "Retune base palettes and audit contrast"). The theme file format stays version 1 readable; if new optional overrides are added, older clients must ignore them.
- **Performance:** switching theme changes one attribute and one variable set (one style recalculation); no per-component theme subscriptions.

## Done when

- [ ] Role names and built-in values come from one source that generates web CSS, mobile themes, desktop window colours and the boot palette; `index.css` theme blocks and the boot copy are generated, not hand-edited.
- [ ] Plane and light roles exist for every built-in, the stock palette with each accent, and a fixture custom theme that defines only today's 60 roles.
- [ ] Automated contrast audit passes (text 4.5:1, large text and icons 3:1, focus 3:1) for stock × 4 accents and five built-ins in both appearances.
- [ ] A fixture set of current custom themes, a VS Code import and a published theme file renders correctly with no stored-data migration.
- [ ] Reserved and unpublishable id lists are preserved and tested; legacy ids resolve.
- [ ] Mobile renders the same built-ins from the generated output (checked on one iOS and one Android build or explicitly deferred to E31-T06).
