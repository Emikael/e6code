# E26-T05 · Environment-published themes

## What it is

A server (an E6 environment) can publish themes and name a default theme for the clients that use it. Published themes appear in the Appearance library as "environment themes", follow the server live as their colours change, and can be duplicated into an editable local copy. The default theme, set with `e6 theme set <id>`, switches each connected web and desktop client once; after that the user's own choice wins until the default is set again. This is how an integration (for example a desktop tool that retints apps when the OS theme changes) keeps E6 Code in step with the rest of a machine.

## When it is used

- A desktop utility on the same machine writes `~/.e6/userdata/themes/<id>.json` every time the wallpaper or system theme changes; E6 Code follows within seconds.
- An admin provisions a team server with a house theme: `e6 theme set nightfall`.
- `e6 theme show` to see which themes and default a server publishes; `e6 theme clear` to remove the default without changing anyone's theme.

## Current screen

No screenshot: the capture server published no themes. Environment theme cards appear in the Appearance library next to built-in and custom themes (see E26-T01).

## How it works today

- **Entry points:** files in `<stateDir>/themes/<id>.json`; CLI `e6 theme set|clear|show`; server setting `defaultTheme` and `defaultThemeSetAt` in `settings.json`; `subscribeServerConfig` event `environmentThemesUpdated` (opt-in per subscriber with `environmentThemes: true`, because older clients cannot decode the event); library cards in Appearance.
- **Server** (`apps/server/src/environmentTheme.ts`, 307 lines): watches the themes directory and streams the published set. The filename is the theme id and stays stable while colours change underneath. Reads use `O_NOFOLLOW` and `O_NONBLOCK`. Limits: 32 files, 32 KB per file, 192 KB total (the whole set travels in one WebSocket event to every subscriber). A file is skipped if invalid or if its id is in `UNPUBLISHABLE_THEME_IDS` (`system`, `light`, `dark`, built-ins, legacy aliases, mobile's `e6-code`). Every failure degrades to "not published". A newly connecting client reads the current set from disk, not from the watcher's last observation.
- **File formats:** a full exported theme file (version 1), or a short format `{ name, appearance: "light"|"dark", canvas, accent, colors? }` from which the rest of the palette is generated; `colors` uses the role names from the editor's Advanced view.
- **CLI** (`apps/server/src/cli/theme.ts`, 589 lines): `set` writes `defaultTheme` and `defaultThemeSetAt` (so re-setting the same value acts again) with a minimal JSON edit that keeps unknown keys, works on a stopped server and on a live one (the server watches `settings.json`); publish commits move files with atomic rename.
- **Client adoption** (`apps/web/src/hooks/useDefaultTheme.ts`): applies a default once per generation (`theme@setAt`), recorded per environment in localStorage `e6code:default-theme-applied:v2:<environmentId>`; waits if the named theme has not been published yet (setting and palette arrive independently); offline clients apply on reconnect. `hooks/useEnvironmentTheme.ts` feeds published themes into the library.
- **Behaviour to preserve:**
  - Only the server that serves the web app, or the desktop app's main local environment, supplies environment themes. The hosted web app (latest.app.e6code.com) and additional connections do not use them.
  - A local custom theme with the same id takes precedence over a published one.
  - If the server stops publishing the selected theme, the client falls back to the standard theme.
  - "Duplicate" makes an independent editable copy; published themes cannot be edited in place.
  - Each `set` switches a client once; a later user choice sticks.
  - Mobile keeps its own appearance and does not follow environment themes or defaults (docs, `cli/theme.ts` header); report 06 lists mobile as a surface, which is inaccurate for adoption.
- **Surfaces:** server, CLI, web and desktop.
- **Where the code lives:** `apps/server/src/environmentTheme.ts`, `apps/server/src/cli/theme.ts`, `packages/contracts/src/environment.ts` (`EnvironmentTheme`, `EnvironmentThemeFile`, `EnvironmentThemeId`), `apps/server/src/serverSettings.ts`, `apps/web/src/hooks/useEnvironmentTheme.ts`, `useDefaultTheme.ts`, `apps/web/src/themePalette.ts` (`getEnvironmentThemes`, `setEnvironmentThemes`), `docs/user/appearance.md` ("Environment themes", "Publish a theme").

## Problems today

- The feature is invisible until a server publishes something; users cannot tell which server a theme card comes from when several environments are connected.
- Generated short-format themes know nothing about planes and light roles.

## Remodel goals

- **Existing published files:** both file formats keep working without change; they gain derived plane and light roles from E26-T02. Any new optional override fields are ignored by older clients and the server's validator must still accept old files.
- **Experience:** environment theme cards say which environment publishes them ("from studio") and show when the server changed the colours; adoption of a default shows a small toast with Undo.
- **Performance:** the published set stays inside today's 192 KB ceiling and is sent only to subscribers that opted in; a recolour sends one event, not one per file.

## Done when

- [ ] Publishing, live recolour, removal fallback, duplicate, precedence of a same-id custom theme and once-per-generation adoption all behave as above (server tests for the watcher limits and id rules; client tests for adoption).
