# E31-T10 · Mobile OTA updates

## What it is

The mobile app updates its JavaScript and assets over the air (OTA) without a store release, using `expo-updates`. Updates download in the background; the app installs them the next time the user leaves it, or immediately if the user agrees. The user docs say: "apps download updates in background; Later defers install."

## When it is used

- A fix ships to the `production` or `preview` channel: phones pick it up on launch or when returning to the app.
- The user sees "Update ready" and chooses "Install Now" or "Later".
- Support asks a user to force a check: tap the version five times in Settings → About E6 Code (E34-T08).

## How it works today

- **Entry points:** automatic check on launch and on foreground; hidden five-tap on the About screen (`registerHiddenUpdateTap`); prompt "Update ready".
- **Behaviour to preserve:**
  - Check on launch, recheck on foreground at most every 15 minutes (`FOREGROUND_APP_UPDATE_RECHECK_AFTER_MS`).
  - Download in the background; then arm a deferred install that runs when the app goes to the background, where nothing is rendering.
  - After 30 minutes with a downloaded update still pending (`DEFERRED_INSTALL_PROMPT_AFTER_MS`), ask: title "Update ready", message "A new version has been downloaded and installs automatically the next time you leave the app. Install it now instead?", buttons "Later" (cancel) and "Install Now".
  - Before restarting, flush pending writes (composer drafts and the thread outbox); an automatic restart aborts if the flush fails ("Could not save pending state."), a user-requested restart proceeds anyway. Failure to reload reports "Downloaded, but could not restart the app." and the update still applies at the next cold start.
  - Only one install sequence runs at a time; a background restart first checks `isSafeToRestartInBackground`.
  - Check-unavailable error codes are treated as "no update", not failures. `fallbackToCacheTimeout: 0`, so launch never waits for the network.
  - Channels per EAS profile (`development`, `preview`, `production`, `v2-preview` with OTA disabled); `runtimeVersion` uses the native fingerprint (appVersion for development), so an update only reaches binaries with matching native code.
- **Platform differences:** same logic on both; the prompt is a native alert on both platforms.
- **Surfaces:** mobile. Web counterpart: none for the client bundle (server and desktop updates are E12-T05 and the desktop epic).
- **Where the code lives:** `apps/mobile/src/features/updates/app-updates.ts` (622; tests 653), `features/settings/SettingsAboutRouteScreen.tsx`; `app.config.ts` (updates URL, runtime version policy), `eas.json` (channels).

## Problems today

- The update state ("downloading", "ready", "restarting") is not visible anywhere except the alert after 30 minutes; there is no quiet indicator.
- The force-check is a hidden gesture.

## Remodel goals

- **Experience:** a quiet "Update ready" row in Settings and an optional unobtrusive banner, instead of an alert as the only surface; an explicit "Check for updates" action in About.
- **Motion:** none beyond the shared banner/snackbar presets.

## Done when

- [ ] All timings, flush rules and failure messages above preserved, with the existing test suite passing against the rebuilt module.
- [ ] Every store with pending writes in the rebuilt app is flushed before restart (registry from E31-T09).
- [ ] Update state visible in Settings; "Later" still defers to the next background.
- [ ] Fingerprint compatibility verified: an update built for a different native fingerprint never installs.
