# E24-T13 · PR service, sync and host providers

## What it is

The server side of pull requests: a **provider layer** that talks to five hosts through their own tools (GitHub `gh`, GitLab `glab`, Azure DevOps `az`, Bitbucket REST API, Forgejo/Gitea `fj` or `tea`), and a **pull request service** that lists, reads, reviews and acts on change requests, caches reads, tracks rate limits, and streams refreshes to clients. Each host declares what it can do (capabilities) and what the signed-in viewer may do (permissions), so clients never offer a dead button.

## When it is used

Behind every PR screen (E24-T01 to T12), git action that opens a PR (E23-T04), publish wizard (E23-T07) and PR sync for linked threads (E24-T11). Also by agents through the MCP PR toolkit.

## How it works today

- **Entry points:** about 28 WS `pullRequests*` RPCs (list, listStats, summary, routing, routingIdentity, stack, linkedThreads, detail, preview, activity, threadComments, diffFileContents, filesViewed, setFilesViewed, runAction, update, comment, updateComment, submitReview, replyToThread, setThreadResolution, setReaction, invalidate, reviewerCandidates, requestReviewers, labelCandidates, setLabels) and the `subscribeRefreshes` stream; `POST /api/pull-requests/diff`; MCP PR tools; `serverDiscoverSourceControl` (which CLIs are installed and signed in; Settings → Source Control → Rescan).
- **Behaviour to preserve:**
  - A read cache single-flights identical reads across WebSocket and HTTP (`PullRequestReadCache.ts`).
  - Rate-limit pause per provider and host with cooldown, and GitHub GraphQL budget tracking; credentials are separated by `CredentialScope`.
  - Shared process limiter: 4 concurrent GitHub processes (with 8 git), 30 s default timeouts.
  - `refreshAfterTurn(projectId)` lets reactors refresh PR state after a turn; sync keys and check summarisation (`pullRequestSyncKey.ts`, `pullRequestChecks.ts`).
  - Viewed-file marks stored on the host (GitHub) or in this server's database (`PullRequestFilesViewed` projection) for the others.
  - GitHub media (images and videos in PR bodies) proxied with the token kept for the GitHub host only, redirects followed manually.
  - `ReviewService` serves review-mode diff previews and file contents for the working tree vs a base (`reviewGetDiffPreview`, `reviewGetDiffFileContents`).
  - Cross-environment GitHub routing: GitHub review details can use another connected environment signed in to the same account (ten-minute verified-credential fallback, no automatic retry of uncertain actions; E29-T09).

## Problems today

- About 19.6k lines across five providers with heavy JSON parsing of host output in Node.
- Each list or detail call spawns a CLI; eager stats sorts multiply calls (E24-T01).
- Capability gaps that are E6's, not the host's (GitLab labels, Bitbucket reactions) are indistinguishable from real host limits.

## Remodel goals

- **Performance:** measure CLI spawns and latency per page view and per sync cycle; bound eager stats; keep large host responses off the event loop (parse cost measured; architecture 3.2 item 3 pattern if needed). Refresh stream sends deltas.
- **Experience:** errors carry a host-specific, actionable hint (sign in, rate limited until HH:MM, missing permission).
