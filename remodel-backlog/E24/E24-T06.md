# E24-T06 · PR review: comments and verdict

## What it is

Reviewing a PR in E6 the way you would on the host: write line comments that stay **pending** (drafted locally) until you submit, reply to and resolve existing review threads, then send the review with a verdict: **Comment**, **Approve** or **Request changes** from a floating review bar.

## When it is used

Code review of a teammate's PR, or a final review of an agent-written PR before merge.

## Current screen

No screenshot: the review bar and pending comments live in the PR Code tab, which could not be reached in the capture environment (see `shots/gitpr/gaps.md`).

In words: a floating bar over the Code tab showing the number of pending comments, a summary field, and the three verdict buttons; pending comments render inline as cards distinct from posted threads.

## How it works today

- **Entry points:** select lines in the Code tab and comment; reply/resolve on an existing thread card; the review bar.
- **Behaviour to preserve:**
  - Pending comments persist locally (`pullRequestReviewStore`, persisted) so a reload does not lose a half-written review.
  - Submitting sends all pending comments with the verdict in one request (`pullRequestsSubmitReview`); replies (`pullRequestsReplyToThread`) and resolve/unresolve (`pullRequestsSetThreadResolution`) are immediate.
  - A summary is required for Request changes; submitting state disables the bar.
  - The bar is hidden on hosts that cannot review.
  - Verdicts offered are the intersection of host capability and viewer permission; on GitHub the PR's own author may only Comment.
- **Per host:**
  - GitHub: inline comments, replies, resolve; Comment, Approve, Request changes.
  - GitLab: inline, reply, resolve; Comment and Approve only (GitLab has no "changes requested").
  - Bitbucket: inline, reply, resolve; all three verdicts.
  - Forgejo/Gitea: inline comments; all three verdicts; **no** replies or resolve (no API).
  - Azure DevOps: no review at all from E6 (no inline comments, replies, resolve or verdicts).
- **Surfaces:** web and desktop. Server: review RPCs in E24-T13.
- **Where the code lives:** `apps/web/src/components/pullRequest/PullRequestReviewBar.tsx` (`:49`), `pullRequestReviewStore.ts`, `PullRequestReviewAnnotation.tsx`, `PullRequestCodeTab.tsx`; contracts `PullRequestReviewCapabilities`.

## Problems today

- Pending comments live in a separate store from the diff panel's review comments (E18-T04), which go to the agent instead of the host: two "comment on a line" models with different destinations and similar UI.
- The bar floats over code and can cover lines.

## Remodel goals

- **Experience:** make the destination unmistakable: "Comment on GitHub" vs "Send to agent" are different actions with different marks. The review bar docks to the panel edge rather than covering the diff.
- **Motion:** submitting lands like a turn: pending cards turn into posted threads with `swap`, the verdict shows with `checkDraw`. Optimistic; never waits on the host.

## Done when

- [ ] Pending persistence, submit with verdict, reply, resolve and per-host gating preserved, with tests per host capability set.
- [ ] Clear separation from agent-bound review comments (decision with E18-T04).
- [ ] Request changes requires a summary; GitHub author restriction kept.
- [ ] Dark and light, keyboard reachable (submit with mod+Enter), reduced motion handled.
