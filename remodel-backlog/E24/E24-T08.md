# E24-T08 · Checks and merge actions

## What it is

Everything that moves a PR toward done: the **checks** popover (CI status), the **merge-readiness** checklist (checks, approval, conflicts, up to date with base, each with a fix action), **Merge** with a method (merge, squash, rebase), **auto-merge**, **Ready for review / Convert to draft**, **Close / Reopen**, **Update branch** (merge or rebase the base in), and two GitHub-only actions: **Approve workflows** for fork PRs and **Revert** a merged PR. Shortcuts copy the PR link or number and open the merge confirmation.

## When it is used

An agent's PR has gone green and the user merges it; checks failed and the user wants to see which; a branch fell behind and needs updating; a merged change must be reverted.

Merging asks "Merge pull request?".

## How it works today

- **Entry points:** detail header and its menu; checks chip on rows and in the header; `pullRequest.merge` (mod+Enter on an open, mergeable PR opens the merge confirmation; also palette "Merge pull request"); `thread.copyReference` (mod+shift+c copies the PR URL) and `pullRequest.copyNumber` (mod+shift+k copies `#n`), searchable as "Copy Link or Thread ID" / "Copy Number"; row context menu.
- **Behaviour to preserve:**
  - All actions go through `pullRequestsRunAction` via a chosen environment ("act on" picker).
  - Merge methods offered = host methods narrowed by repository settings (`mergeCapabilities`) and the user's default (`pullRequestMergeMethod`, per-project overrides).
  - Readiness tiers (`resolveMergeReadiness`), base freshness (`resolveBaseFreshness`), primary control choice (`resolvePullRequestPrimaryControl`).
  - Confirm dialogs for merge, revert, approve workflows and similar; host-specific failure hints in toasts.
  - Auto-merge toasts: "Auto-merge turned on — merges as soon as this is ready, sooner if it already is" / "Auto-merge turned off".
  - After update-branch the diff is refreshed (`pullRequestActionNeedsHostRefresh`).
  - Checks summary: "No checks reported", loading, failing with Fix (E24-T10).
- **Per host:**
  - GitHub: merge/squash/rebase; ready, draft, close, reopen; update branch by merge or rebase; auto-merge; revert; approve fork workflows.
  - GitLab: merge/squash/rebase (narrowed by project setting); ready, draft, close, reopen; update branch by rebase only; auto-merge (merge when pipeline succeeds).
  - Bitbucket: merge/squash/rebase; close (decline) only. No reopen, no draft toggle, no update branch, no auto-merge.
  - Azure DevOps: merge or squash; ready, draft, close, reopen; auto-merge (auto-complete); no update branch.
  - Forgejo/Gitea: merge/squash/rebase; close, reopen; update branch by merge or rebase; no draft toggle, no auto-merge.
- **Surfaces:** web and desktop. Server: E24-T13.
- **Where the code lives:** `apps/web/src/components/pullRequest/PullRequestDetailPanel.tsx`, `pullRequestDetail.logic.ts`, `pullRequestMergeCommand.ts`, `PullRequestChecksPopover.tsx` (`:109`), `pullRequestChecks.test.tsx`; server `pullRequest/pullRequestChecks.ts`, `*PullRequestProvider.ts` (capability tables).

## Problems today

- Many actions in one header with container-query hide/show rules; hard to see which one is next.
- Check details can be stale ("Check details are out of date") with no clear refresh cue.

## Remodel goals

- **Experience:** the checklist is the header: each unmet item names the fix and the button for it; Merge becomes the primary action only when ready. Destructive and history-changing actions (revert, rebase update) always confirm.
- **Motion:** "Merging lands like a turn: `checkDraw`, the row's mark swaps to Merged in the merged role, no celebration" (design direction 8). Running checks use the live mark only while running.
