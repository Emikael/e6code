# E24-T12 · PR link routing and project assignment

## What it is

Two pieces of routing. **Open PR links** decides, for any PR URL clicked in E6 (markdown links, chips, toasts), whether to open it in the in-app PR panel or in the browser, by matching the URL's host and repository to a project. **PR to project assignment** maps a PR's repository to a project on an environment (including the same project on several servers) and chooses the environment to act through.

## When it is used

Clicking `#142` in an agent's message; opening a PR found on the list in the right project context; acting on a PR that two connected servers can both reach.

## How it works today

- **Entry points:** any PR URL in markdown, chips and toasts (`openPullRequestLink`); native context menu on PR links ("Open on host", copy link, link to thread); `useOpenPanelPullRequestUrl`.
- **Behaviour to preserve:**
  - Matching rules by host and port (Forgejo instances on non-default ports included) and repository; no match opens the browser.
  - The right-panel PR surface persists per thread (`rightPanelStore.ts`).
  - Assignment handles duplicates across environments and picks the environment to act on; scope helpers `resolveProjectScope`, `findScopedProject` on the list page.
- **Surfaces:** web and desktop (desktop context menu is native via `localApi.contextMenu`).
- **Where the code lives:** `apps/web/src/lib/openPullRequestLink.ts` (358), `hooks/useOpenPanelPullRequestUrl.ts`, `components/pullRequest/pullRequestLinkContextMenu.ts`, `pullRequestProjectAssignment.logic.ts`, `pullRequestProjectFilter.logic.ts`, `routes/_chat.pull-requests.tsx`.

## Problems today

- When no project matches, the user silently goes to the browser with no hint that linking a remote would enable in-app review.
- `rightPanelStore` persists one blob for all threads (architecture 3.2 item 13).

## Remodel goals

- **Experience:** PR links behave the same everywhere; when they leave the app, a small "Open in E6" affordance or reason is offered where possible.
