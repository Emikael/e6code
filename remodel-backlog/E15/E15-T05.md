# E15-T05 · Queue, steer and stop

## What it is

While an agent is working, the user can still write. A message sent during a run is either **queued** (shown as a dashed "queued" bubble at the end of the timeline and sent at the next natural break) or used to **steer** (delivered to the running turn right away so the agent changes course). Which one happens is a setting, and a modifier flips it for one message. **Stop** interrupts the running turn and returns any queued messages to the composer so nothing starts by surprise.

## When it is used

- Adding "also update the docs" while the agent is mid-task, without interrupting it.
- Correcting an agent heading the wrong way ("no, use the existing helper").
- Stopping a run that has gone off track.

## How it works today

- **Entry points:** Enter while running (behaviour per Settings → General → Follow-up behavior: Queue or Steer, default Queue); Mod+Enter does the opposite for one message (Mod+Shift+Enter when Send shortcut needs Mod+Enter); `thread.steerQueuedMessage` (`mod+shift+enter`) sends the oldest queued message now; queued bubble buttons (arrow "Send now", × "move back to composer"); Stop button in the composer and in the ThreadNow line (E13-T13); `thread.stop` keybinding (no default); stop one subagent is `thread.stopSubagent` (`mod+.`, E13-T11).
- **Behaviour to preserve:**
  - A queued message carries a full snapshot of the draft (text, images, files, terminal contexts, annotations, review comments, intent) and the ID of the newest completed tool activity at queue time.
  - Release rule: the oldest queued message leaves when a tool call completes after it was queued, or when the turn ends. Only one message leaves per tool boundary; the rest are re-anchored (`take` re-anchors to the new tool activity).
  - The queue holds while an approval or question is pending (a steer would answer nothing), and while transient gates are closed (environment offline, settings not hydrated, checkpoint rewinding, detail loading, load balancing pending, provider status unknown); it resumes when they clear.
  - "Send now" steers that message immediately; × removes it and puts its content back in the composer.
  - Stop interrupts the turn and drains every queued message back into the composer; messages restored by Stop or a failed send are held (`holdUntilUserAction`) and wait for "Send now" instead of leaving on their own. A failed send puts the message back at the head so nothing behind it overtakes.
  - A send that took a message before Stop and finishes its upload after Stop gives up (`drainGeneration`), so Stop cannot be followed by a new turn.
  - The web queue is in memory only: a reload loses queued messages (by design: "a queued message is a live intent"). Mobile persists queued messages in an offline outbox that survives restarts.
  - **Steering per provider:** a send while a turn runs is a steer in every adapter. Claude folds the message into the running turn; Cursor reuses the active turn; Grok cancels the in-flight ACP prompt and re-prompts immediately; OpenCode queues the prompt inside its own session; Antigravity drains the cancelled prompt before steering; Codex's mechanism is not verified (its app-server rejects same-turn steering during `/review` or manual `/compact`).
- **Surfaces:** web and desktop. Mobile: queued-message feedback with edit-while-queued and the outbox (E32-T03). Server: interrupt and steer through orchestration and adapters.
- **Where the code lives:** `apps/web/src/queuedMessageStore.ts` (201), `ChatView.tsx:7690-7765, 8122-8150, 9100-9165` (queue, release, steer, remove), `ChatView.tsx:4153-4226` (`onInterrupt`), `MessagesTimeline.tsx:2014` (queued row), `components/chat/ComposerPrimaryActions.tsx`, `chat/threadStopCommands.ts`.

## Problems today

- Queue logic is spread through ChatView effects and refs.
- Queued messages vanish on reload without warning on web, while mobile keeps them.
- The difference between queue and steer is hard to see; the bubble does not say when it will leave.

## Remodel goals

- **Experience:** the running composer state (design direction §8 Composer) makes Stop the primary action and shows a visible queue count; each queued bubble says "Sends after the current step" or "Held: send now?" in words. Stop confirms what happened ("Stopped. 2 queued messages returned to the composer").
- **Motion:** enqueuing is a user-caused move: the prompt travels from the composer to the queued bubble (`matchCut`) or cuts; when a queued message leaves, its bubble becomes the sent message in place (no fade-out elsewhere).
- **Performance:** release checks run on tool-completion events, not on every streamed delta.
