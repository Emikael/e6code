# E15-T04 · Usage limits and handoff to a new thread

## What it is

Subscription plans for coding agents have usage limits (for example a five-hour window and a weekly window). This task covers how a thread shows those limits and what the user can do when one is hit. The `/usage-limits` command shows the current model's limits in a notice above the composer. When a provider reports that the limit is reached, a banner offers **Continue in new thread**: a dialog that starts a new thread on another provider instance, model and effort, seeded with a summary of the current conversation (including image resources), reusing the same branch and worktree. Claude instead pauses the thread with "Paused for usage limit · resets in 1h 12m" and continues after the reset unless stopped.

## When it is used

- Checking how much of a plan is left before a long task.
- Hitting a Codex or Claude limit mid-task and wanting to keep going on another account or provider.
- Waiting out a short Claude reset.

## How it works today

- **Entry points:** `/usage-limits` typed in the composer (intercepted by the send pipeline, no turn sent); the usage-limit banner in the banner stack (E14-T09) with "Continue in new thread"; the Claude agent-state label with countdown in the timeline (E13-T09/T13); Usage → Limits page (E28-T02).
- **Behaviour to preserve:**
  - `/usage-limits` renders per-provider limit info for the current model above the composer (`ComposerUsageLimits.tsx`), from usage-limit sources in `@e6tools/client-runtime`. Limit checks run automatically per environment at most every five minutes.
  - Codex limit notice names the exhausted window and the reset time, plus a workspace-plan credits notice; Codex reset credits can be used from Usage (E28).
  - Handoff targets: picker-ready instances other than the thread's source instance, in picker order, each with its last-used or default model; targets that are also limited are flagged; selection validated before start.
  - The handoff preview carries over context including image resources (`selectHandoffImageResources`); the new thread reuses the branch and worktree; the original thread is untouched. Where the summary is generated (client or server) is not verified.
  - Claude pause: thread shows "Paused for usage limit · resets in …" and resumes after the reset; the user can stop and continue later.
  - **Per provider (E37-T11):** Codex native rate-limit events plus fetcher and reset credits; Claude native events plus fetcher and the pause state; Cursor via billing API with a stored token (`CURSOR_AUTH_TOKEN` or file CLI login); Grok from local login credentials; OpenCode Go local only; Antigravity none (quota errors appear as messages); API-key accounts do not report limits.
- **Surfaces:** web and desktop. Mobile: `ComposerUsageLimits` report and `ThreadHandoffCard` with `thread-handoff-selection.ts` (E32-T09, E32-T06). Server: limit sources and fetchers (E28-T04).
- **Where the code lives:** `apps/web/src/components/chat/ComposerUsageLimits.tsx` (124), `ThreadHandoffDialog.tsx` (159), `ComposerHandoff.tsx` (28), `ChatView.tsx:3252, 3271, 6736-6948`, `session-logic.ts:1605`, `packages/client-runtime/src/state/agentState.ts` (pause label), `@e6tools/client-runtime/state/thread-handoff`.

## Problems today

- Handoff logic (targets, preview, creation) is about 200 lines inline in `ChatView.tsx`.
- Limit information is reachable only by typing `/usage-limits` or opening the Usage page; there is no glanceable indicator before hitting the wall.
- Provider-specific branches decide the pause versus handoff behaviour.

## Remodel goals

- **Experience:** reaching a limit is a "landing" (design direction §3.5 rule 5: failure is a landing, not an alarm): the frontier says what happened, when it resets, and offers the handoff as the primary next action. The handoff dialog previews what carries over.
- **Motion:** dialog uses the standard dialog preset; the countdown text updates once a minute, nothing animates while waiting.

## Done when

- [ ] `/usage-limits`, the limit banner, the Claude pause label and the handoff dialog behave as above for every provider that reports limits; providers that do not report say so.
- [ ] Handoff target selection, validation and context carry-over are a shared module (web and mobile) with tests.
- [ ] The new thread reuses branch and worktree; the source thread is untouched.
- [ ] Dark and light reviewed; dialog keyboard reachable.
